This activity puts into practice the concepts from the [Monitoring, Alerting, and Observability](/lectures/monitoring-and-performance/) lecture. You will use minikube as a local cluster, install Prometheus and Grafana with Helm, scrape a small service that you control, build a three-panel dashboard, and watch an alert fire when that service disappears. By the end, you will have a lighter-weight monitoring stack on your laptop and a concrete example of how Helm packages monitoring software for Kubernetes.

---

## What You Will Need

- The [Minikube](/activities/minikube/) activity completed once already, or `minikube`, `kubectl`, and Docker installed from the official guides
- `helm` installed. Use the install guide at [helm.sh/docs/intro/install/](https://helm.sh/docs/intro/install/).
- Two terminal windows or tabs
- A web browser
- About 6 GiB of free RAM for Docker plus the local cluster

<Aside type="note" title="Why this activity uses a lighter stack">
The later lab uses `kube-prometheus-stack`, which is a realistic cluster-monitoring bundle but also a large install with many moving parts. This activity keeps the local version smaller by using separate Prometheus and Grafana charts, which is enough to practice Helm, scraping, dashboards, and alerts without the full operator stack.
</Aside>

## Start the Cluster and Install the Helm Releases

Before you look at any metrics, bring up a clean local monitoring environment. In this section you will start minikube, write two small values files, and install Prometheus and Grafana as Helm releases.

<Steps>

1. **Verify the tools you will use throughout the activity:**

   ```bash
   docker version
   minikube version
   kubectl version --client
   helm version
   ```

   Each command should print version information and return you to the prompt. Fix any missing tool before you continue.

2. **Make sure minikube is running:**

   ```bash
   minikube status
   ```

   If the cluster is stopped, start it now:

   ```bash
   minikube start --driver=docker --memory=4096 --cpus=2
   ```

   When minikube is ready, `kubectl get nodes` should show one node in the `Ready` state.

3. **Create a working directory for this activity:**

   ```bash
   mkdir -p ~/cs312-monitoring
   cd ~/cs312-monitoring
   ```

   Keep the Helm values files and manifests from this activity here.

4. **Write the Prometheus values file:**

   ```bash
   cat <<'EOF' > prometheus-values.yaml
   alertmanager:
     enabled: false

   kube-state-metrics:
     enabled: false

   prometheus-node-exporter:
     enabled: false

   prometheus-pushgateway:
     enabled: false

   server:
     persistentVolume:
       enabled: false

   serverFiles:
     alerting_rules.yml:
       groups:
         - name: podinfo.rules
           rules:
             - alert: PodinfoMissing
               expr: absent(up{service="podinfo", namespace="observability"})
               for: 1m
               labels:
                 severity: warning
               annotations:
                 summary: "podinfo metrics target disappeared"
                 description: "Prometheus has not seen the podinfo target in the observability namespace for 1 minute."
   EOF
   ```

   This file keeps the Prometheus install small and also defines one alert rule up front. The alert is not for a node or exporter; it is for the specific service you will deploy later.

5. **Write the Grafana values file:**

   ```bash
   cat <<'EOF' > grafana-values.yaml
   adminPassword: cs312grafana

   persistence:
     enabled: false

   datasources:
     datasources.yaml:
       apiVersion: 1
       datasources:
         - name: Prometheus
           type: prometheus
           url: http://metrics-prometheus-server.monitoring.svc.cluster.local
           access: proxy
           isDefault: true

   service:
     type: ClusterIP
   EOF
   ```

   This pre-provisions the Prometheus data source so you do not have to create it by hand in the UI.

6. **Add the Helm repositories and install the two releases:**

   ```bash
   helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
   helm repo add grafana-community https://grafana-community.github.io/helm-charts
   helm repo update

   helm install metrics prometheus-community/prometheus \
     --namespace monitoring \
     --create-namespace \
     -f prometheus-values.yaml

   helm install grafana grafana-community/grafana \
     --namespace monitoring \
     -f grafana-values.yaml
   ```

   You should now have two Helm releases in the `monitoring` namespace: one for Prometheus and one for Grafana.

7. **Verify the releases and wait for the Pods to be ready:**

   ```bash
   helm list -n monitoring
   kubectl get pods -n monitoring -w
   ```

   Wait until the Prometheus server and Grafana show `Running`. Press `Ctrl+C` when the watch settles down.

8. **Start two port-forwards so you can use the web interfaces:**

   In one terminal:

   ```bash
   kubectl -n monitoring port-forward svc/grafana 3000:80
   ```

   In a second terminal:

   ```bash
   kubectl -n monitoring port-forward svc/metrics-prometheus-server 9090:80
   ```

   Keep both terminals open. Grafana will be available at `http://127.0.0.1:3000` and Prometheus at `http://127.0.0.1:9090`.

</Steps>

## Deploy a Service and Let Prometheus Discover It

Now you need something that produces application metrics. In this section you will deploy `podinfo`, expose its metrics on a separate port, and let Prometheus discover that endpoint by reading annotations on a Kubernetes Service.

<Steps>

1. **Write the workload manifest:**

   ```bash
   cat <<'EOF' > podinfo.yaml
   apiVersion: v1
   kind: Namespace
   metadata:
     name: observability
   ---
   apiVersion: apps/v1
   kind: Deployment
   metadata:
     name: podinfo
     namespace: observability
     labels:
       app: podinfo
   spec:
     replicas: 1
     selector:
       matchLabels:
         app: podinfo
     template:
       metadata:
         labels:
           app: podinfo
       spec:
         containers:
           - name: podinfo
             image: ghcr.io/stefanprodan/podinfo:6.11.2
             command:
               - ./podinfo
               - --level=info
               - --port=9898
               - --port-metrics=9797
             ports:
               - name: http
                 containerPort: 9898
               - name: metrics
                 containerPort: 9797
             readinessProbe:
               httpGet:
                 path: /readyz
                 port: http
             livenessProbe:
               httpGet:
                 path: /healthz
                 port: http
   ---
   apiVersion: v1
   kind: Service
   metadata:
     name: podinfo
     namespace: observability
     annotations:
       prometheus.io/scrape: "true"
       prometheus.io/port: "9797"
       prometheus.io/path: "/metrics"
   spec:
     selector:
       app: podinfo
     ports:
       - name: http
         port: 9898
         targetPort: http
       - name: metrics
         port: 9797
         targetPort: metrics
   EOF
   ```

   The Service annotations are the important part. They tell Prometheus that this Service should be scraped and which port exposes metrics.

2. **Apply the manifest and wait for the Deployment to become ready:**

   ```bash
   kubectl apply -f podinfo.yaml
   kubectl rollout status deployment/podinfo -n observability
   kubectl get pods,svc -n observability
   ```

   Continue only after the Pod is available and the Service exists.

3. **Open a local port-forward to the application itself:**

   In a third terminal:

   ```bash
   kubectl -n observability port-forward svc/podinfo 9898:9898
   ```

   Keep that terminal open too. You will use `http://127.0.0.1:9898` for test traffic.

4. **Confirm that Prometheus discovered the new target:**

   Open `http://127.0.0.1:9090/targets` in your browser. Look for a target from the `observability` namespace with the `podinfo` Service name.

   The state should become `UP` within a minute. That is the scrape relationship you created with three Service annotations, not with a hand-edited `prometheus.yml`.

5. **Run a simple query to confirm the target exists:**

   In the Prometheus expression browser, run:

   ```promql
   up{service="podinfo", namespace="observability"}
   ```

   A value of `1` means the scrape succeeded. A value of `0` would mean the target exists but is failing to scrape.

</Steps>

## Generate Traffic and Build a Dashboard

Once the target is being scraped, make it do something interesting. In this section you will generate successful requests, failing requests, and slow requests, then turn those measurements into three dashboard panels in Grafana.

<Steps>

1. **Send a burst of mixed traffic to the service:**

   ```bash
   for i in {1..20}; do curl -s http://127.0.0.1:9898/ >/dev/null; done
   for i in {1..5}; do curl -s http://127.0.0.1:9898/status/500 >/dev/null; done
   for i in {1..5}; do curl -s http://127.0.0.1:9898/delay/1 >/dev/null; done
   ```

   This gives you three things to measure immediately: total request rate, error rate, and latency.

2. **Check the metrics directly in Prometheus first:**

   Run these queries in the Prometheus expression browser:

   ```promql
   sum(rate(http_requests_total[1m]))
   ```

   ```promql
   sum(rate(http_requests_total{status=~"5.."}[1m]))
   ```

   ```promql
   histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[1m])))
   ```

   The first query is total request rate, the second is 5xx rate, and the third is p95 latency.

3. **Log into Grafana and create a dashboard:**

   Open `http://127.0.0.1:3000`. Log in with:

   - Username: `admin`
   - Password: `cs312grafana`

   Create a new dashboard with three time-series panels.

4. **Add the three queries as dashboard panels:**

   Use these panel titles and queries:

   - `Request rate`

     ```promql
     sum(rate(http_requests_total[1m]))
     ```

   - `5xx rate`

     ```promql
     sum(rate(http_requests_total{status=~"5.."}[1m]))
     ```

   - `p95 latency`

     ```promql
     histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[1m])))
     ```

   Set the dashboard time range to the last 15 minutes so the burst you just created stays visible.

5. **Generate a second burst of traffic while watching the dashboard refresh:**

   ```bash
   for i in {1..10}; do curl -s http://127.0.0.1:9898/ >/dev/null; done
   for i in {1..3}; do curl -s http://127.0.0.1:9898/status/500 >/dev/null; done
   ```

   Within the next refresh interval, the request-rate and 5xx panels should jump again.

</Steps>

## Watch an Alert Fire and Recover

Dashboards are useful only when someone is looking at them. Alerts are what bring attention to a problem when nobody is watching. In this section you will use the alert rule you installed through Helm values and trigger it by removing the application target completely.

<Steps>

1. **Open the Prometheus alerts page:**

   Visit `http://127.0.0.1:9090/alerts` in your browser.

   You should see the `PodinfoMissing` rule listed, but not firing.

2. **Confirm where that rule came from:**

   ```bash
   helm get values metrics -n monitoring
   ```

   You should see the alert definition under `serverFiles.alerting_rules.yml`. This is the local version of configuration-as-code for an alert rule.

3. **Scale the Deployment to zero replicas:**

   ```bash
   kubectl scale deployment/podinfo --replicas=0 -n observability
   kubectl get pods -n observability -w
   ```

   Watch until the Pod disappears. Then return to the Prometheus alerts page.

4. **Wait for the rule to move from Pending to Firing:**

   The expression uses `absent(...)` and the rule has `for: 1m`, so the alert should first show as Pending and then change to Firing after one minute.

5. **Restore the service:**

   ```bash
   kubectl scale deployment/podinfo --replicas=1 -n observability
   kubectl rollout status deployment/podinfo -n observability
   ```

   After the Pod returns and Prometheus scrapes it again, the alert should clear.

</Steps>

## Clean Up or Leave the Cluster Running

At this point you have a working local monitoring stack. You can remove the demo workload now, or you can leave the monitoring namespace in place if you want to use the same minikube cluster for the later Loki and Fluent Bit activity.

<Steps>

1. **Delete the demo application namespace:**

   ```bash
   kubectl delete namespace observability --wait=true
   ```

   This removes the application you monitored while leaving Prometheus and Grafana in place.

2. **Optionally stop the three port-forwards:**

   If you still have the `kubectl port-forward` commands running in other terminals, press `Ctrl+C` in each of them.

3. **Decide whether to keep the monitoring stack installed:**

   If you want to use the later logging activity, leave the `monitoring` namespace and the minikube cluster running.

   If you want to remove the monitoring releases now, run:

   ```bash
   helm uninstall grafana -n monitoring
   helm uninstall metrics -n monitoring
   kubectl delete namespace monitoring --wait=true
   ```

</Steps>

## Going Further

You have now installed two Helm charts, provisioned one alert rule through a values file, and turned raw metrics into a dashboard. The next step up in complexity is to move from a single instrumented service to cluster-level monitoring with the Prometheus Operator, ServiceMonitors, and PrometheusRules managed as Kubernetes objects rather than static files inside one server chart.

If you want to keep going locally, compare this activity's two-release setup to the `kube-prometheus-stack` chart used later in the course. Run `helm show values prometheus-community/kube-prometheus-stack | less` and notice how much more of the Kubernetes ecosystem it packages for you at once. If you want to broaden from metrics into logs, keep the same minikube cluster and add Loki plus Fluent Bit so Grafana can answer both "what is broken?" and "why did it break?" from one interface.
