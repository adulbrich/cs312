This activity puts into practice the concepts from the [Network Services and Application Delivery](/lectures/network-services-and-application-delivery/) lecture. You will manipulate DNS records live to see TTL and negative-caching behavior, read email authentication and TLS certificate records on real domains, trace CDN behavior through HTTP headers, and build a path-routing reverse proxy with Docker Compose. By the end, you will have directly observed each major layer of the application delivery stack in action.

## DNS Records and TTL

[Mess with DNS](https://messwithdns.net/) gives you a personal subdomain where you control all the records. You can add, remove, and modify records through a web interface and immediately query the results with `dig`. This makes TTL propagation and record types directly observable rather than abstract.

<Steps>
1. Open [messwithdns.net](https://messwithdns.net/) in a browser. The site assigns you a random subdomain such as `fuzzy-owl-1234.messwithdns.net`. Write it down; you will use it in every `dig` command in this section.

2. Find the authoritative nameserver for `messwithdns.net`. This server holds the current zone data for your subdomain, and querying it directly bypasses any resolver caching:

   ```bash
   dig +short NS messwithdns.net
   ```

   Record the nameserver hostname returned. You will substitute it for `<NS>` in later steps.

3. In the Mess with DNS interface, create an **A record** for your subdomain. Set the value to `203.0.113.1` and the TTL to `300`.

   `203.0.113.1` is from RFC 5737, reserved for documentation examples. It is safe to publish in a test zone.

4. Query a public recursive resolver for your new record:

   ```bash
   dig YOUR-SUBDOMAIN.messwithdns.net @1.1.1.1
   ```

   In the ANSWER SECTION, note the TTL value. That number is how many seconds Cloudflare's resolver will cache this answer before issuing a fresh query to the authoritative server.

5. Now query the authoritative server directly:

   ```bash
   dig YOUR-SUBDOMAIN.messwithdns.net @<NS>
   ```

   The authoritative server returns the current record value immediately and does not cache. The difference between this query and the previous one is exactly the distinction between "the record changed" and "every resolver on the internet has the new value."

6. In the Mess with DNS interface, change the **TTL** on the A record from `300` to `30`, but keep the IP address at `203.0.113.1` for now. Then query both servers again:

   ```bash
   dig A YOUR-SUBDOMAIN.messwithdns.net @<NS>
   dig A YOUR-SUBDOMAIN.messwithdns.net @1.1.1.1
   ```

   The authoritative server shows the new TTL immediately. The recursive resolver may still show a much higher remaining TTL from the earlier 300-second cache entry. Lowering TTL is not retroactive: you have to wait for the old cached answer to expire before the lower TTL takes effect at that resolver.

7. Add an **AAAA record** for your subdomain pointing to `2001:db8::1` with TTL `300`. Confirm both records exist at the authoritative server:

   ```bash
   dig A YOUR-SUBDOMAIN.messwithdns.net @<NS>
   dig AAAA YOUR-SUBDOMAIN.messwithdns.net @<NS>
   ```

   A domain with both A and AAAA records is dual-stack. A stale AAAA record pointing nowhere can break only IPv6 clients while IPv4 works fine, which makes the outage appear intermittent when viewed from a single protocol.

8. Add a **TXT record** for your subdomain with the following text:

   ```
   v=spf1 ip4:203.0.113.1 -all
   ```

   Query for it:

   ```bash
   dig TXT YOUR-SUBDOMAIN.messwithdns.net @<NS>
   ```

   This is the format of a real SPF record. The `-all` qualifier at the end is a hard fail: any sender not explicitly listed should be rejected. Your subdomain has no real mail servers, so this policy is consistent with that.

9. Add an **MX record** for your subdomain. Set the mail server to `mail.example.com.` (include the trailing dot) and the priority to `10`.

   ```bash
   dig MX YOUR-SUBDOMAIN.messwithdns.net @<NS>
   ```

   The priority number in the answer determines preference: lower is tried first. A domain with MX records at priorities 10 and 20 uses priority 10 as the primary and priority 20 as the fallback.

10. **Demonstrate TTL propagation.** Re-run the recursive query from step 6 until the TTL in its ANSWER SECTION has counted down to `30` or lower. Then change the A record IP address from `203.0.113.1` to `203.0.113.2`.

    Query both the authoritative server and the public resolver immediately after making the change:

    ```bash
    # Authoritative server: always current
    dig +short A YOUR-SUBDOMAIN.messwithdns.net @<NS>

    # Recursive resolver: may still show the old answer
    dig +short A YOUR-SUBDOMAIN.messwithdns.net @1.1.1.1
    ```

    The authoritative server returns the new IP right away. The public resolver may briefly keep the old IP, but once it refreshes its now-low-TTL cache, the new answer should appear within about 30 seconds rather than up to 5 minutes.

11. Observe **negative caching** with a name that does not exist yet. Query a fresh label under your subdomain, such as `missing`:

    ```bash
    dig missing.YOUR-SUBDOMAIN.messwithdns.net @1.1.1.1
    ```

    You should get `NXDOMAIN`. In the AUTHORITY SECTION, note the zone's SOA record and its TTL. That TTL is how long the resolver may cache the "does not exist" answer. On this platform it is often much longer than the 30-second positive TTL you just used, which is why accidentally testing a name before creating it can make a new record appear broken for much longer than expected.

    Do not create this `missing` record during class. The whole point of this check is to see that negative answers can be cached too.
</Steps>

## Email Authentication Records

SPF, DKIM, and DMARC rely on DNS records published at well-known locations, but they do different jobs. SPF authenticates the SMTP envelope domain, DKIM signs the message, and DMARC ties those checks to the visible `From:` domain. This section reads those records on real domains with `dig` so you can see what a production mail authentication setup looks like at the DNS layer.

<Steps>
1. Look up the SPF record for `google.com`. SPF lives as a TXT record at the domain root:

   ```bash
   dig TXT google.com +short
   ```

   You will see several TXT records. Find the one starting with `v=spf1`. It names the hosts authorized to send mail for Google's SMTP envelope domain. The qualifier at the end controls enforcement: `-all` is a hard fail (reject unauthorized senders), `~all` is a soft fail (accept but treat as suspicious).

2. Look up the DMARC record for `google.com`. DMARC always lives at the `_dmarc` subdomain:

   ```bash
   dig TXT _dmarc.google.com +short
   ```

   Find the `v=DMARC1` record. Record the `p=` policy: `reject` instructs receiving servers to discard messages that fail alignment; `quarantine` routes them to spam; `none` logs failures but takes no action.

3. Look up the DMARC policy for a second domain and compare:

   ```bash
   dig TXT _dmarc.mit.edu +short
   ```

   Note the `p=` value and compare it to Google's. A `p=none` policy means the domain is collecting DMARC reports to audit its sending sources before committing to enforcement. Organizations typically run `p=none` while discovering all legitimate senders, then move to `p=quarantine` or `p=reject` once confident.

4. Check the MX records for `google.com` to see how Gmail routes incoming mail:

   ```bash
   dig MX google.com +short
   ```

   You will see multiple records at different priority values. The sending mail server tries the lowest-priority record first and falls back to higher-numbered records if the primary is unreachable.

5. Check whether `example.com` publishes a NULL MX record:

   ```bash
   dig MX example.com +short
   ```

   A response of `0 .` is a NULL MX record. It tells senders explicitly not to attempt delivery to this domain. Without it, some senders fall back to the domain's A record when no MX exists, creating an unintended delivery path.
</Steps>

## CDN Behavior from the Outside

A CDN inserts edge servers between clients and the origin so that traffic reaches a nearby PoP rather than traveling to a single data center. This section shows what that insertion looks like from a client: CDN IP addresses in DNS, cache status in HTTP headers, and TLS termination at the edge rather than at the origin.

<Steps>
1. Look up the IP addresses for `aws.amazon.com`:

   ```bash
   dig +short aws.amazon.com
   ```

   These are CloudFront edge addresses, not the IP of a single web server in one location. Clients in different geographic regions receive different IPs, each routing to the nearest CloudFront PoP.

2. Fetch the HTTP headers from the same site and look for CDN fingerprints:

   ```bash
   curl -sI https://aws.amazon.com/ | grep -iE "server:|x-cache:|x-amz-cf"
   ```

   `X-Cache` shows CloudFront's decision for this response. `Hit from cloudfront` means the edge served a cached copy; `Miss from cloudfront` means the edge had to fetch from the origin. `X-Amz-Cf-Pop` names the specific CloudFront edge location that served it.

   <Aside type="note" title="CDN headers by provider">
   Header names are provider-specific. CloudFront uses `X-Cache` and `X-Amz-Cf-Pop`. Cloudflare uses `CF-Cache-Status` and `CF-Ray`. Fastly uses `X-Served-By`. The exact cache status varies by resource and over time, but the presence of provider-specific headers confirms a CDN is in the path.
   </Aside>

3. Fetch headers from a Cloudflare-hosted static resource to compare naming conventions:

   ```bash
   curl -sI https://developers.cloudflare.com/robots.txt | grep -iE "cf-ray:|cf-cache-status:|server:"
   ```

   `CF-Ray` is a unique identifier for this request's path through Cloudflare's network. `CF-Cache-Status` reports Cloudflare's cache decision for this response. On a static resource like this, you will often see `HIT` or `MISS`.

4. Fetch headers from a dynamic Cloudflare page and compare the status value:

   ```bash
   curl -sI https://blog.cloudflare.com/ | grep -iE "cf-ray:|cf-cache-status:|server:"
   ```

   A value such as `DYNAMIC` means Cloudflare was in the path but did not serve a cached copy. `HIT` means the edge returned cached content. `MISS` means the edge had to fetch from the origin.

5. Check what TLS certificate the CDN presents at the edge:

   ```bash
   openssl s_client -connect aws.amazon.com:443 -servername aws.amazon.com 2>/dev/null \
     | openssl x509 -noout -issuer -subject
   ```

    For `aws.amazon.com`, the issuer is currently an Amazon CA. The important point is that this certificate is presented by CloudFront at the edge PoP rather than by a single origin server. A CloudFront distribution can use an ACM certificate or an imported certificate for the viewer-facing connection, and the origin can use a different certificate on the private connection from CloudFront to the backend.
</Steps>

## TLS Certificate Inspection

A TLS certificate contains the hostnames it covers, the chain of trust back to a root CA, the validity window, and a Certificate Transparency log entry. This section reads those fields directly on a live server so you can recognize each one when debugging a certificate failure.

<Steps>
1. Connect to Oregon State's web server and capture the key certificate fields:

   ```bash
   openssl s_client -connect oregonstate.edu:443 -servername oregonstate.edu 2>/dev/null \
     | openssl x509 -noout -issuer -dates -ext subjectAltName
   ```

   You will see the issuing CA, the validity window (`notBefore` to `notAfter`), and the Subject Alternative Names: the full list of hostnames this certificate covers.

    Note whether both `oregonstate.edu` and either `www.oregonstate.edu` explicitly or a wildcard such as `*.oregonstate.edu` appear in the SAN list. A certificate issued only for the apex domain would produce a hostname mismatch error for clients that connect to `www.`.

2. Verify that the certificate chain is complete and trusted:

   ```bash
   openssl s_client -connect oregonstate.edu:443 -servername oregonstate.edu 2>/dev/null \
     | grep "Verify return code"
   ```

   `Verify return code: 0 (ok)` means the full chain validated against your system's trust store. Any other code indicates a problem: an expired certificate, a missing intermediate, or a hostname mismatch.

3. Look up the Certificate Transparency log entries for this domain in a browser:

   ```
   https://crt.sh/?q=oregonstate.edu
   ```

   You will see publicly logged certificates matching this domain search, with issuance dates and issuing CAs. Every publicly trusted certificate issued since 2018 must appear in a CT log: browsers reject certificates that have not been logged.

   Notice how frequently certificates appear in the log and which CA issued each one. A domain using Let's Encrypt will show a new entry approximately every 90 days because that is the maximum certificate lifetime.

4. Check whether `oregonstate.edu` restricts which CAs are authorized to issue certificates for the domain:

   ```bash
   dig CAA oregonstate.edu +short
   ```

   A CAA record such as `0 issue "letsencrypt.org"` tells every other CA that Let's Encrypt is the only authorized issuer. If another CA issues a certificate anyway, CT monitoring catches it because the certificate must appear in a public log.

   If the query returns nothing, there is no CAA record and any CA can issue for this domain.
</Steps>

## Reverse Proxy Path Routing

A reverse proxy routes incoming requests to different backends based on the content of the HTTP request. This section builds a three-container setup: one nginx instance acting as a Layer 7 proxy, and two nginx instances acting as separate backends with different content. The proxy reads the URL path from each HTTP request and forwards it to the matching backend.

Create a working directory for this section:

```bash
mkdir -p ~/cs312-delivery && cd ~/cs312-delivery
```

### Set Up the Files

<Steps>
1. Create `web.html`. Replace `YOUR_ONID` with your actual ONID:

   ```html
   <!doctype html>
   <html>
   <head><meta charset="utf-8"><title>Web</title></head>
   <body>
   <h1>Web backend</h1>
   <p>Owner: YOUR_ONID</p>
   </body>
   </html>
   ```

2. Create `api.html`:

   ```html
   <!doctype html>
   <html>
   <head><meta charset="utf-8"><title>API</title></head>
   <body>
   <h1>API backend</h1>
   <p>Status: ok</p>
   </body>
   </html>
   ```

3. Create `proxy.conf`. This is the nginx configuration that makes the proxy a Layer 7 router:

   ```nginx
   server {
       listen 80;

       location /api/ {
           proxy_pass http://api/;
           add_header X-Served-By "api-backend";
       }

       location / {
           proxy_pass http://web/;
           add_header X-Served-By "web-backend";
       }
   }
   ```

   The two `location` blocks are the routing rules. nginx reads the URL path from the incoming HTTP request and forwards to a different upstream depending on which block matches. `X-Served-By` is added to each response to make the routing decision visible.

4. Create `docker-compose.yml`:

   ```yaml
   services:
     proxy:
       image: nginx:1.27-alpine
       ports:
         - "8080:80"
       volumes:
         - ./proxy.conf:/etc/nginx/conf.d/default.conf
       depends_on:
         - web
         - api

     web:
       image: nginx:1.27-alpine
       volumes:
         - ./web.html:/usr/share/nginx/html/index.html

     api:
       image: nginx:1.27-alpine
       volumes:
         - ./api.html:/usr/share/nginx/html/index.html
   ```

   Only the `proxy` service has a `ports` mapping. The `web` and `api` containers listen on port 80 inside Docker's internal bridge network, but that port is not exposed to the host. All external traffic must enter through the proxy.
</Steps>

### Observe the Routing

<Steps>
1. Start all three containers:

   ```bash
   docker compose up -d
   ```

   Docker Compose creates a shared bridge network, starts `web` and `api`, then starts `proxy`. The proxy resolves `http://web/` and `http://api/` using Docker's internal DNS, which maps each service name to its container IP.

2. Verify all three containers are running:

   ```bash
   docker compose ps
   ```

   All three services should show `running`. Note that only `proxy` shows a host port mapping. The `web` and `api` services have no port mappings: there is no address on your host that routes to them directly. The proxy is the only entry point.

3. Test the path routing. Both requests go to the same host and port; the proxy forwards each to a different backend based on the path:

   ```bash
   # Root path goes to the web backend
   curl -s http://localhost:8080/

   # API path goes to the api backend
   curl -s http://localhost:8080/api/
   ```

   You will see different HTML content for each path. The proxy read the URL path from the HTTP request to make that forwarding decision. A Layer 4 load balancer operating on IP addresses and port numbers would have no visibility into the path and could not make this distinction.

4. Confirm the routing with the response headers:

   ```bash
   curl -sI http://localhost:8080/ | grep X-Served-By
   curl -sI http://localhost:8080/api/ | grep X-Served-By
   ```

   The first response should carry `X-Served-By: web-backend`. The second should carry `X-Served-By: api-backend`. The proxy added that header inside the matching `location` block, which is why the value differs by path.

5. Follow the proxy access log live in one terminal:

   ```bash
   docker compose logs -f proxy
   ```

   Leave this running. Every request that enters the proxy will appear here immediately.

6. In a second terminal, send the two requests again:

   ```bash
   curl -s http://localhost:8080/ >/dev/null
   curl -s http://localhost:8080/api/ >/dev/null
   ```

   You will see two new log lines appear in the proxy log, one for `/` and one for `/api/`. This centralized record is one of the main operational advantages of routing all traffic through a proxy: instead of checking logs on every backend separately, you have one stream that shows the full request history for the entire application. Press `Ctrl+C` in the log terminal when you are ready to continue.
</Steps>

Run this command to produce a clean visible result with your identifier:

```bash
curl -s http://localhost:8080/ | grep -i owner
```

Your ONID should appear in the output, confirming your personalized web backend is live and reachable through the proxy.

When you are done, stop and remove the containers:

```bash
docker compose down
```

## Going Further

You have directly observed TTL propagation in a live DNS zone, read production email authentication and TLS records with `dig` and `openssl`, traced CDN cache behavior through HTTP headers, and routed requests through a Layer 7 proxy. The natural next step on the proxy side is to add automatic TLS.

[Caddy](https://caddyserver.com/docs/getting-started) replaces the nginx proxy with a server that handles certificate issuance and renewal automatically. On a machine with a public IP and a domain name pointed at it, Caddy requests a certificate from Let's Encrypt during first startup and renews it without any additional tooling. To see the difference in operational overhead, rewrite this activity's proxy configuration as a `Caddyfile` and compare the number of moving parts required to serve the same routes over HTTPS.

To see the CDN proxy layer from the owner's side rather than the client's, Cloudflare offers a free tier for any domain you control. Once you point a test domain's nameservers at Cloudflare, `dig` queries return Cloudflare edge addresses, `curl -I` responses include `CF-Ray` and `CF-Cache-Status`, and Cloudflare's dashboard shows the edge PoP that served each request. The techniques from the CDN section of this activity apply directly to your own traffic.
