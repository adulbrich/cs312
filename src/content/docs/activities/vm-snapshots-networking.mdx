</Aside>

## Part 1: The Snapshot Safety-Net Workflow

**Lecture concept:** Snapshots and Clones.

The lecture describes snapshots as short-lived rollback tools for risky changes. This part makes you run that workflow end-to-end.

### Step A: Confirm a Healthy Baseline

Power on the VM if it is off. Log in and run:

```bash
sudo systemctl status ssh
df -h /
```

Both should show normal output (SSH active, root filesystem with free space).

### Step B: Take a Pre-Change Snapshot

Take a snapshot named `pre-change-1`.

<Tabs>
<TabItem label="UTM">
<Steps>
1. Right-click the VM in the UTM sidebar.
2. Select **Snapshot > New Snapshot**.
3. Name it `pre-change-1` and confirm.
</Steps>
</TabItem>
<TabItem label="VirtualBox">
<Steps>
1. With the VM selected, open **Machine > Take Snapshot**.
2. Name it `pre-change-1` and click **OK**.
</Steps>
</TabItem>
</Tabs>

<Aside type="note">
A snapshot marks the current disk image read-only and starts writing only changed blocks to a new delta file. The full disk is not copied, which is why snapshots are fast — but it also means they share the same storage pool as the base image.
</Aside>

### Step C: Make a Destructive Change

Simulate a misconfiguration by corrupting the SSH service config:

```bash
sudo sh -c 'echo "Port INVALID_VALUE" >> /etc/ssh/sshd_config'
sudo systemctl reload ssh
```

Verify the damage:

```bash
sudo systemctl status ssh
sudo sshd -T 2>&1 | head -5
```

The status should show a failure or reload error. The sshd config check should show a configuration error.

### Step D: Attempt an In-Place Fix (and Give Up)

Try to find and fix the bad line — but act as if you cannot locate it quickly:

```bash
tail -10 /etc/ssh/sshd_config
```

You can see the `Port INVALID_VALUE` line. In a real incident, it might not be this obvious. This is the decision point: spend more time debugging, or revert to the known-good snapshot.

### Step E: Revert the Snapshot

Shut down the VM:

```bash
sudo shutdown -h now
```

Revert to `pre-change-1`:

<Tabs>
<TabItem label="UTM">
<Steps>
1. Right-click the VM and select **Snapshot > Restore Snapshot**.
2. Select `pre-change-1` and confirm.
</Steps>
</TabItem>
<TabItem label="VirtualBox">
<Steps>
1. Open the **Snapshots** panel for the VM.
2. Right-click `pre-change-1` and choose **Restore**.
3. Uncheck **Create snapshot of current state** and click **Restore**.
</Steps>
</TabItem>
</Tabs>

Start the VM. Verify recovery:

```bash
sudo systemctl status ssh
sudo sshd -T 2>&1 | head -3
tail -5 /etc/ssh/sshd_config
```

All three should be clean — SSH active, no config error, no `INVALID_VALUE` line.

<Aside type="caution">
Snapshots are not backups. The snapshot and the base disk share the same storage pool. If the host machine's disk fails, both are lost. Backups must reside on separate storage.
</Aside>

### Step F: Delete the Snapshot

Once recovery is confirmed, delete `pre-change-1`:

<Tabs>
<TabItem label="UTM">
<Steps>
1. Right-click the VM and select **Snapshot > Delete Snapshot**.
2. Select `pre-change-1` and confirm.
</Steps>
</TabItem>
<TabItem label="VirtualBox">
<Steps>
1. Open the **Snapshots** panel.
2. Right-click `pre-change-1` and choose **Delete Snapshot**.
</Steps>
</TabItem>
</Tabs>

<Aside type="tip">
Delete snapshots once they are no longer needed. Long snapshot chains add read overhead because each read must check the delta file before falling back to the base image.
</Aside>

## Part 2: Networking Modes

**Lecture concept:** Networking Modes.

### Observe NAT Behavior

Your VM currently uses NAT.

<Steps>
1. Check the VM's IP address:

   ```bash
   ip addr show
   ```

   Note the address (typically `10.0.2.15` on VirtualBox, varies on UTM).

2. From your **laptop's** terminal (not the VM), try to reach the VM:

   ```bash
   ping -c 3 <vm-ip-address>
   ```

   This will time out on most NAT configurations. The VM can reach outward; nothing can reach in without port forwarding.

3. Test that the VM can still reach the internet — run this **inside the VM**:

   ```bash
   ping -c 3 debian.org
   ```
</Steps>

### Switch to Host-Only Networking

<Steps>
1. Power off the VM:

   ```bash
   sudo shutdown -h now
   ```

2. Change the network adapter:

   <Tabs>
   <TabItem label="UTM">
   <Steps>
   1. Open **VM Settings > Network**.
   2. Change the mode from **Shared Network** to **Host Only**.
   3. Save and start the VM.
   </Steps>
   </TabItem>
   <TabItem label="VirtualBox">
   <Steps>
   1. Open **Settings > Network > Adapter 1**.
   2. Change **Attached to** from **NAT** to **Host-only Adapter**.
   3. Select `vboxnet0` from the adapter list, then click **OK**.
   4. Start the VM.
   </Steps>
   </TabItem>
   </Tabs>

3. Check the new IP address inside the VM:

   ```bash
   ip addr show
   ```

4. Test reachability from your **laptop**:

   ```bash
   ping -c 3 <new-vm-ip>
   ```

   This should succeed.

5. Test internet access from **inside the VM**:

   ```bash
   ping -c 3 debian.org
   ```

   This will fail. Host-only means the host and guest can communicate, but the guest is isolated from the broader network.
</Steps>

## Reflection Questions

1. **Snapshot mechanics:** When you took the snapshot, the hypervisor made the base disk read-only. Where did subsequent writes go? What happened to those writes when you reverted?
2. **Snapshot overhead:** The lecture says long chains degrade read performance because reads must traverse layers. Why does a snapshot chain add read overhead even when no data has been overwritten?
3. **NAT trade-off:** Why is NAT the default for a laptop VM? What would you need to configure to host a web server accessible from other machines while using NAT?
4. **Bridged networking risk:** The lecture notes that bridged mode on Wi-Fi can fail if the access point blocks unknown MAC addresses. Why would a Wi-Fi AP block an unknown MAC, and how would you work around it in a lab environment?
