This activity puts the concepts from the [Virtualization and Virtual Machines](/lectures/virtualization-basics/) lecture into practice across four parts. By the end you will have a running Debian VM, have executed the snapshot safety-net workflow, observed how networking modes affect connectivity, and researched how the major hypervisors compare.


## What You Will Need

- A laptop with at least 8 GB of RAM and 20 GB of free disk space
- Administrator access to your laptop
- An internet connection

## Set Up the Virtual Machine

### Install a Hypervisor

A hypervisor is the software layer that creates and manages virtual machines on your laptop. Without it, there is no way to run a second operating system alongside your host OS. We will use a **Type-2 (hosted) hypervisor**, meaning it runs as a regular application on top of your existing operating system. We will use **VirtualBox**, which runs on macOS, Windows, and Linux.

<Steps>
1. Download VirtualBox from [virtualbox.org](https://www.virtualbox.org/wiki/Downloads) and install it.
2. Also install the **VirtualBox Extension Pack** from the same page (enables USB 3.0 and other features).
3. Open VirtualBox. You do not need to create a VM yet.
</Steps>

<Aside type="note" title="macOS alternative: UTM">
On macOS you can also use [UTM](https://mac.getutm.app/), which is a frontend for QEMU and supports both ARM and x86-64 guests. VirtualBox works on Apple Silicon as well, so we standardize on it here for consistency across platforms.
</Aside>

### Download a Guest OS ISO

An ISO file is a disk image: a single file that contains the exact contents of a bootable installation disc. The hypervisor can present this file to the VM as if it were a physical DVD drive, so the VM boots the installer without any physical media. We will use the **Debian 12 (Bookworm)** server netinstall ISO. Debian installs quickly, runs with a low memory footprint, and is available for both ARM and x86-64.

<Tabs>
<TabItem label="Apple Silicon Mac (ARM)">
Download the `arm64` netinstall ISO from [cdimage.debian.org](https://cdimage.debian.org/debian-cd/current/arm64/iso-cd/).

Look for a filename like `debian-12.x.x-arm64-netinst.iso`.
</TabItem>
<TabItem label="Intel Mac / Windows / Linux (x86-64)">
Download the `amd64` netinstall ISO from [cdimage.debian.org](https://cdimage.debian.org/debian-cd/current/amd64/iso-cd/).

Look for a filename like `debian-12.x.x-amd64-netinst.iso`.
</TabItem>
</Tabs>

<Aside type="note" title="Architecture matters">
Always match the ISO architecture to your host CPU. VirtualBox on Apple Silicon runs ARM64 guests natively at near-native speed. Running an x86-64 ISO on Apple Silicon would require full instruction emulation, which is much slower.
</Aside>

### Create the Virtual Machine

Before starting the installer, we define the VM's virtual hardware: how many vCPUs, how much RAM, and how large a virtual disk. These choices shape the VM's behavior for the rest of the activity. The goal is to start conservative (not generous) because it is easy to increase resources later and because over-allocating on a laptop starves your host OS.

<Steps>
1. Click **New**.
2. Name: `debian-lab`. Type: **Linux**. Version: **Debian (64-bit)** on Intel/Windows/Linux, or **Debian (arm64)** on Apple Silicon.
3. Hardware:
   - Memory: **1024 MB**
   - Number of CPUs: **2**
   - Disk Size: **20 GB** (you can use less but partitioning might be finicky for this specific activity)
   - **Use EFI**
4. After the VM is created, open **Settings > Network > Adapter 1** and set **Adapter Type** to **Paravirtualized Network (virtio-net)**. VirtualBox defaults to an emulated Intel NIC; VirtIO gives you a paravirtualized network adapter instead.
</Steps>

<Aside type="tip" title="Why these resource sizes">
A Debian server install with no GUI uses about 700 MB of RAM at idle. Starting at 1 GB provides enough headroom to observe memory behavior without over-provisioning. Two vCPUs mirrors what you would typically allocate to a small server VM.
</Aside>

</ActivityQuestion>

### Install Debian

Starting the VM boots the Debian installer from the ISO, exactly as if you had inserted a DVD into a real machine. The VM window becomes the VM's virtual monitor: it shows only what the virtual machine is outputting. Your laptop's own desktop continues running normally behind it.

<Steps>
1. Start the VM. The Debian boot menu appears in the VM window. Select **Install** to use the text-mode installer.

   <Aside type="note" title="GUI vs. text installer">
   The installer also offers a **Graphical install** option, which adds a mouse-driven interface over the same steps. Either works for this activity. In production, servers rarely have a monitor attached at all and are configured entirely over SSH after first boot; we are deliberately installing without a desktop to mirror that reality.
   </Aside>

2. Follow the installer prompts:
   - Language: English
   - Location: United States
   - Keyboard: American English (or whatever matches your physical keyboard)
   - Hostname: `debian-lab`
   - Domain name: leave blank
   - Root password: set one you will remember
   - New user: create a regular account (you can use your ONID username, e.g., `ulbrical`) with a password
   - Timezone: Pacific (or your local timezone)
   - Partitioning: **Guided - use entire disk**, then **All files in one partition**
   - Package manager mirror: United States - debian.osuosl.com
   - Software selection: uncheck everything except **SSH server** and **standard system utilities**

   The software selection step is significant. Deselecting the desktop environment means the installed system boots to a text prompt with no graphical interface. This is a deliberate choice that reflects real server practice: a GUI consumes memory, installs more software (more attack surface), and is simply unnecessary on a machine you will manage remotely.

3. Let the installer finish. It downloads packages from the internet during installation (5-15 minutes depending on network speed).

4. When prompted, eject the ISO and reboot.
</Steps>

### Using the VM's Terminal

After reboot, the VM window shows a plain text login prompt: no desktop, no mouse cursor. This is the **virtual console**: the equivalent of a physical keyboard and monitor directly connected to a server. Type your username and press Enter, then enter your password (it will not echo to the screen; this is normal).

Everything in the sections below is typed into this console. The VM's terminal behaves exactly like any Linux terminal: commands you type run inside the VM, not on your laptop. Your host OS is completely unaffected by anything you do here. This isolation is the whole point of a VM.

<Aside type="tip" title="Releasing the cursor">
If you accidentally click outside the VM window and your mouse or keyboard stops responding to the VM, click inside the VM window to recapture input. The VirtualBox status bar shows the host key combination (default: Right Ctrl) to release the cursor if it gets captured.
</Aside>

### Verify Paravirtualized Drivers

The hypervisor can expose virtual hardware to the guest in two ways: fully emulated (slower, universally compatible) or paravirtualized (faster, requires a cooperative driver in the guest). Here we check which type is active for storage and networking, because the difference is measurable.

**Check the storage driver:**

```bash
lsblk -d -o NAME,TYPE,TRAN
```

`lsblk` lists block devices, which are the kernel's view of storage hardware. The `-d` flag shows disks only (no partitions), and `-o NAME,TYPE,TRAN` selects the columns: device name, type, and transport protocol.

You will see something like this:

```
NAME TYPE TRAN
sda  disk
sr0  rom
```

The disk appears as `sda` because VirtualBox uses a VirtIO SCSI controller, which uses SCSI device naming (`sda`, `sdb`, ...) rather than the virtio-blk naming (`vda`). The TRAN column is empty because lsblk does not report a transport for virtio. To confirm the virtio controller is actually active, check the PCI devices:

```bash
lspci | grep -i virtio
```

You should see a line containing `Virtio SCSI` for storage and `Virtio network` for networking.

**Install guest utilities and ethtool:**

<Aside type="note" title="sudo vs. su: Debian vs. Ubuntu">
Ubuntu pre-installs `sudo` and disables direct root login by default, so you never need `su`. Debian takes the opposite approach: `sudo` is not installed on a fresh system, and root has a real password you set during installation. To run commands as root on Debian, use `su -` (the `-` loads root's full environment, including the correct `PATH`) and then run commands directly without any prefix. If you later want `sudo`-style access, you can install it with `apt install sudo` and add your user to the `sudo` group.
</Aside>

```bash
su -
apt update
apt install ethtool
```

`apt update` refreshes the package index from Debian's servers. Without this step, `apt install` would use a stale index and might not find the latest versions. `ethtool` is a utility for querying network interface driver information.

**Check the network driver:**

```bash
# Show all network interfaces
ip link show
# Substitute your non-loopback interface name from the output above
ethtool -i enp0s3 | grep driver
# Expected output: driver: virtio_net
```

`ip link show` lists every network interface on the machine. You will see at least two: `lo` (the loopback interface, used for traffic that stays within the machine) and your main network interface (named something like `enp0s3`, `eth0`, or `ens3`; the exact name depends on the hypervisor and the kernel's device detection order).

`ethtool -i` queries driver information for a network interface. The `driver:` line tells you which kernel module is managing the device. `virtio_net` confirms paravirtualized networking is active; `e1000` or `pcnet32` would indicate a fully-emulated NIC.

### Collect Baseline Metrics

Before making any changes to a system, record what "normal" looks like. This baseline is your reference point: if something feels slow later, you can compare current numbers to these. The commands below each measure one aspect of system health.

```bash
# CPU: idle percentage over a short sample
top -b -n 3 | grep "Cpu(s)" | tail -1
```

`top` is an interactive process viewer. The `-b` flag runs it in batch mode (non-interactive, suitable for capturing output) and `-n 3` tells it to sample 3 times then exit. Each sample produces a `Cpu(s)` line showing percentages for user time, system time, and idle time. We take the last of the three samples with `tail -1`. A freshly booted VM should show high idle (90%+).

```bash
# Memory: used vs available
free -h
```

`free -h` shows memory usage in human-readable units. The key column is **available**: this is what the kernel estimates is realistically free for new processes, including memory currently used for disk cache that would be released if needed. "Available" is almost always lower than "total" because the kernel eagerly uses free RAM for caching. This is normal and healthy behavior: unused RAM is wasted RAM.

```bash
# Disk: used space on root filesystem
df -h /
```

`df -h /` shows how much of the root filesystem is used. The `Use%` column is what to watch over time. On a freshly installed Debian system, this should be well under 20%.

```bash
# Uptime and load average
uptime
```

`uptime` reports how long the system has been running and three **load average** figures (1-minute, 5-minute, 15-minute). Load average is a rolling count of processes waiting to run. On a 2-vCPU VM, a sustained load average above 2.0 indicates the CPU is saturated.

Record all these values. You will refer back to them in later activities when diagnosing whether a service is having a measurable impact on system resources.

</ActivityQuestion>

## The Snapshot Safety-Net Workflow

Before making any risky change to a running system, a snapshot gives you a guaranteed rollback path. Rather than spending time carefully reversing each change if something goes wrong, you revert the entire disk to the pre-change state in seconds. This part runs that workflow end-to-end so the steps are instinctive before you need them in a real scenario.

### Confirm a Healthy Baseline

Log in to the VM and verify the SSH service and disk state are clean before creating the snapshot. Taking a snapshot of a broken system is not useful.

```bash
systemctl status ssh
df -h /
```

Both should show normal output: SSH active and running, root filesystem with free space.

### Take a Pre-Change Snapshot

<Steps>
1. With the VM selected, open **Snapshots**, right click on "Current State" and click "Take...".
2. Name it `pre-change-1` and click **OK**.
</Steps>

<Aside type="note" title="How snapshots work">
When you take a snapshot, the hypervisor marks the current disk image read-only and creates a new delta file to receive all subsequent writes. Reads still come from the original image for blocks that have not changed; new or changed blocks go to the delta. This is why snapshots are nearly instant: the full disk is not copied.
</Aside>

### Make a Destructive Change

We will simulate a common real-world mistake: a typo in a configuration file that breaks a service. In practice this could be a misconfigured firewall rule, a bad nginx config, or an incorrect database connection string. Here we corrupt the SSH service config with an invalid port value.

```bash
sh -c 'echo "Port INVALID_VALUE" >> /etc/ssh/sshd_config'
systemctl reload ssh
```

Verify the damage:

```bash
systemctl status ssh
sshd -T
```

`systemctl status ssh` will show the service as still **active (running)** but with the reload marked as failed. This is intentional: sshd is designed to keep the existing process alive when a reload fails, so active SSH sessions are not dropped. The damage is in the config, not yet in the running process.

`sshd -T` runs the SSH daemon in test mode, validating the config without starting a daemon. You should see a single line such as `Badly formatted port number`.

### Attempt an In-Place Fix (and Give Up)

```bash
tail -10 /etc/ssh/sshd_config
```

`tail -n` prints the last n lines of a file. You can see the `Port INVALID_VALUE` line at the end. In this simple case the culprit is obvious. In a real incident the bad line might be buried in a 200-line config file that was auto-generated by a deployment script, or the problem might be an interaction between two valid-looking settings. This is the decision point: keep debugging, or spend five seconds reverting to the confirmed-working state.

### Revert the Snapshot

Shut down the VM gracefully before reverting (e.g., `shutdown now`), since most hypervisors require the VM to be powered off to restore a snapshot.

Revert to `pre-change-1`:

<Steps>
1. Open the **Snapshots** panel for the VM.
2. Right-click `pre-change-1` and choose **Restore**.
3. Uncheck **Create snapshot of current state** and click **Restore**.
</Steps>

Start the VM and verify recovery:

```bash
systemctl status ssh
sshd -T
tail -5 /etc/ssh/sshd_config
```

All three should be clean: SSH active, no config error, no `INVALID_VALUE` line.

<Aside type="caution" title="Snapshots are not backups">
Snapshots are not backups. The snapshot and the base disk share the same storage pool on the host. If the host machine's disk fails, both are lost simultaneously. Backups must reside on entirely separate storage.
</Aside>

### Delete the Snapshot

Once recovery is confirmed and you are satisfied the system is working, delete the snapshot:

<Steps>
1. Open the **Snapshots** panel.
2. Right-click `pre-change-1` and choose **Delete Snapshot**.
</Steps>

Deleting a snapshot merges the delta file back into the base image and removes the extra layer. Snapshots are meant to be short-lived: the longer you keep one, the larger the delta grows, and the more layers the hypervisor must traverse on every disk read.

## Networking Modes

The networking mode you assign to a VM determines what it can reach and what can reach it. This matters immediately: if you configure a VM to host a service, the networking mode decides whether other machines on your network can connect. This part lets you observe the practical difference between NAT and host-only directly.

### Observe NAT Behavior

Your VM currently uses NAT. In NAT mode, the hypervisor acts like a router: the VM gets a private IP address on a virtual network, and the hypervisor forwards outbound traffic on the VM's behalf using the host's real IP address. This means the VM looks like the host to the outside world.

<Steps>
1. Check the VM's IP address:

   ```bash
   ip addr show
   ```

   `ip addr show` lists all network interfaces with their assigned addresses. Look for an `inet` line on your non-loopback interface. The address is typically `10.0.2.15` on VirtualBox. Note that this is a private address in a virtual subnet managed entirely by the hypervisor.

2. From your **laptop's** terminal (not inside the VM), try to ping the VM:

   ```bash
   ping -c 3 <vm-ip-address>
   ```

   This will time out. The VM can initiate connections outward, but nothing outside the hypervisor's virtual network can initiate a connection to the VM. The hypervisor has no port-forwarding rule telling it where to send incoming packets addressed to the VM.

3. Confirm the VM still has outbound internet access; run this **inside the VM**:

   ```bash
   ping -c 3 debian.org
   ```

   This should succeed: the VM can reach out through the hypervisor's NAT, even though the reverse direction is blocked.
</Steps>

<ActivityQuestion>
The ping from your laptop to the VM times out even though the VM can reach the internet. Explain why using the concept of NAT. What would you need to configure to SSH into the VM from your laptop while it is in NAT mode?
</ActivityQuestion>

### Switch to Host-Only Networking

Host-only creates a private virtual network that exists only between the host and its guests. There is no connection to the physical network or the internet; the hypervisor does not perform NAT. This mode is useful for lab setups where you want VMs to communicate with each other and with your laptop, but you do not want them reachable from outside.

<Steps>
1. Power off the VM:

   ```bash
   shutdown now
   ```

2. Change the network adapter to host-only:

   <Steps>
   1. In the main VirtualBox Manager window, open the **Network** tab (separate from the VM) and click **Create** to add a host-only network if none exists.
   2. Open your VM **Settings > Network > Adapter 1**.
   3. Change **Attached to** from **NAT** to **Host-only Network** and select the network you just created.
   4. Click **OK** and start the VM.
   </Steps>

3. Check the new IP address inside the VM:

   ```bash
   ip addr show
   ```

   The address will be on a different subnet than NAT, typically `192.168.x.x` for host-only.

4. From your **laptop**, ping the VM:

   ```bash
   ping -c 3 <new-vm-ip>
   ```

   This should succeed. Your laptop and the VM are on the same virtual host-only network.

5. From **inside the VM**, test internet access:

   ```bash
   ping -c 3 debian.org
   ```

   This will fail. The host-only network has no default gateway pointing to the internet; traffic has nowhere to go beyond the host. You can test the host's IP on the host-only network to confirm the VM can still reach the host:

   ```bash
   ping -c 3 <host-only-ip-of-host>
   ```

   That IP address is typically the gateway for the host-only network, and it should respond to pings from the VM.
</Steps>

</ActivityQuestion>
