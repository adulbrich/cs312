This activity puts the concepts from the [Virtualization and Virtual Machines](/lectures/virtualization-basics/) lecture into practice across four parts. By the end you will have a running Debian VM, have executed the snapshot safety-net workflow, observed how networking modes affect connectivity, and researched how the major hypervisors compare.

<Aside type="tip">
Keep the [Virtualization and Virtual Machines](/lectures/virtualization-basics/) lecture open as a reference. Each section below notes which lecture concept it exercises.
</Aside>

## What You Will Need

- A laptop with at least 8 GB of RAM and 20 GB of free disk space
- Administrator access to your laptop
- An internet connection

## Part 1: Set Up the Virtual Machine

### Install a Hypervisor

<Tabs>
<TabItem label="macOS (UTM)">
<Steps>
1. Download UTM from [mac.getutm.app](https://mac.getutm.app/) or install via Homebrew:
   ```bash
   brew install --cask utm
   ```
2. Open UTM. You do not need to create a VM yet.
</Steps>
</TabItem>
<TabItem label="Windows / Linux (VirtualBox)">
<Steps>
1. Download VirtualBox from [virtualbox.org](https://www.virtualbox.org/wiki/Downloads) and install it.
2. Also install the **VirtualBox Extension Pack** from the same page (enables USB 3.0 and other features).
3. Open VirtualBox. You do not need to create a VM yet.
</Steps>
</TabItem>
</Tabs>

### Download a Guest OS ISO

We will use the **Debian 12 (Bookworm)** server netinstall ISO. Debian installs quickly, runs with a low memory footprint, and is available for both ARM and x86-64.

<Tabs>
<TabItem label="Apple Silicon Mac (ARM)">
Download the `arm64` netinstall ISO from [cdimage.debian.org](https://cdimage.debian.org/debian-cd/current/arm64/iso-cd/).

Look for a filename like `debian-12.x.x-arm64-netinst.iso`.
</TabItem>
<TabItem label="Intel Mac / Windows / Linux (x86-64)">
Download the `amd64` netinstall ISO from [cdimage.debian.org](https://cdimage.debian.org/debian-cd/current/amd64/iso-cd/).

Look for a filename like `debian-12.x.x-amd64-netinst.iso`.
</TabItem>
</Tabs>

<Aside type="note">
**Lecture connection: virtualization vs. emulation:** On Apple Silicon, running the ARM Debian ISO is **virtualization** (same architecture, near-native speed via Apple's Hypervisor framework). Running the x86-64 ISO on the same machine would be **emulation** (instruction translation, much slower). Always match the ISO architecture to your host CPU when you want performance.
</Aside>

### Create the Virtual Machine

<Tabs>
<TabItem label="UTM (macOS)">
<Steps>
1. Click **Create a New Virtual Machine**.
2. Choose **Virtualize** (not Emulate; you want hardware-accelerated performance with a matching-architecture guest).
3. Operating System: **Linux**.
4. Boot ISO: select the Debian ISO you downloaded.
5. Hardware:
   - **CPU Cores:** 2
   - **Memory:** 1024 MB
6. Storage: **8 GB** (dynamic).
7. Leave shared directory empty. Name the VM `debian-lab` and save.
</Steps>
</TabItem>
<TabItem label="VirtualBox (Windows / Linux)">
<Steps>
1. Click **New**.
2. Name: `debian-lab`. Type: **Linux**. Version: **Debian (64-bit)**.
3. Memory: **1024 MB**.
4. Create a Virtual Hard Disk: VDI format, **Dynamically allocated**, **8 GB**.
5. Open **Settings** for the new VM:
   - **System > Processor:** 2 CPUs.
   - **System > Motherboard:** Enable EFI.
   - **Storage:** Under the optical drive, select the Debian ISO.
   - **Network:** Adapter 1 set to **NAT** (the default).
</Steps>
</TabItem>
</Tabs>

<ActivityQuestion>
You configured 2 vCPUs and 1 GB of RAM. Why start this small rather than giving the VM half your laptop's resources? What risk does the lecture describe if you overcommit CPU or memory on the host?
</ActivityQuestion>

### Install Debian

<Steps>
1. Start the VM and boot from the ISO. Select **Install** (text mode) from the boot menu.

2. Follow the installer prompts:
   - Language: English
   - Location: your country
   - Hostname: `debian-lab`
   - Root password: set one you will remember
   - New user: create a regular account (e.g., `labuser`)
   - Partitioning: **Guided — use entire disk**, then **All files in one partition**
   - Software selection: uncheck everything except **SSH server** and **standard system utilities**

3. Let the installer finish. It downloads packages during installation (5–15 minutes depending on network speed).

4. When prompted, eject the ISO and reboot.
</Steps>

<Aside type="note">
Choosing "SSH server only, no desktop" is exactly what the Linux server planning lecture describes as a server installation: no graphical desktop, lower memory footprint, smaller attack surface.
</Aside>

### Verify Paravirtualized Drivers

Log in to the VM and check what storage driver is active:

```bash
lsblk -d -o NAME,TYPE,TRAN
```

On a VM with virtio storage you will see a `vda` device rather than `sda` (emulated SATA). The `vda` prefix confirms `virtio-blk` is in use.

Install the QEMU guest agent and ethtool:

```bash
sudo apt update
sudo apt install qemu-guest-agent ethtool
sudo systemctl enable --now qemu-guest-agent
```

Check the network driver (find your interface name first, then inspect its driver):

```bash
ip link show

# Substitute your non-loopback interface name (e.g. enp0s3, eth0)
ethtool -i enp0s3 | grep driver
# Expected output: driver: virtio_net
```

<ActivityQuestion>
The storage device appears as `vda` instead of `sda`. What hardware is `virtio-blk` replacing, and why is it faster than the fully-emulated alternative? What would you need to do to confirm the network driver is also using virtio?
</ActivityQuestion>

### Collect Baseline Metrics

```bash
# CPU: idle percentage over a short sample
top -b -n 3 | grep "Cpu(s)" | tail -1

# Memory: used vs available
free -h

# Disk: used space on root
df -h /

# Uptime and load average
uptime
```

Record these values. The habit of noting "normal" before changes is what lets you recognize "abnormal" when something goes wrong.

<ActivityQuestion>
The `free -h` output shows less than 1 GB available, even though you allocated 1 GB to the VM. Where did the rest go? Is this a problem, and how would you tell if the VM were actually memory-constrained?
</ActivityQuestion>

## Part 2: The Snapshot Safety-Net Workflow

The lecture describes snapshots as short-lived rollback tools for risky changes. This part runs that workflow end-to-end.

### Confirm a Healthy Baseline

Log in to the VM and verify the SSH service and disk state are clean:

```bash
sudo systemctl status ssh
df -h /
```

Both should show normal output: SSH active, root filesystem with free space.

### Take a Pre-Change Snapshot

<Tabs>
<TabItem label="UTM">
<Steps>
1. Right-click the VM in the UTM sidebar.
2. Select **Snapshot > New Snapshot**.
3. Name it `pre-change-1` and confirm.
</Steps>
</TabItem>
<TabItem label="VirtualBox">
<Steps>
1. With the VM selected, open **Machine > Take Snapshot**.
2. Name it `pre-change-1` and click **OK**.
</Steps>
</TabItem>
</Tabs>

<Aside type="note">
A snapshot marks the current disk image read-only and starts writing only changed blocks to a new delta file. The full disk is not copied, which is why snapshots are fast, but both the delta and the base image live on the same physical disk.
</Aside>

### Make a Destructive Change

Simulate a misconfiguration by corrupting the SSH service config:

```bash
sudo sh -c 'echo "Port INVALID_VALUE" >> /etc/ssh/sshd_config'
sudo systemctl reload ssh
```

Verify the damage:

```bash
sudo systemctl status ssh
sudo sshd -T 2>&1 | head -5
```

The status should show a failure or reload error.

### Attempt an In-Place Fix (and Give Up)

```bash
tail -10 /etc/ssh/sshd_config
```

You can see the `Port INVALID_VALUE` line. In a real incident, the bad config might not be obvious. This is the decision point: spend more time debugging, or revert to the known-good snapshot.

### Revert the Snapshot

Shut down the VM:

```bash
sudo shutdown -h now
```

Revert to `pre-change-1`:

<Tabs>
<TabItem label="UTM">
<Steps>
1. Right-click the VM and select **Snapshot > Restore Snapshot**.
2. Select `pre-change-1` and confirm.
</Steps>
</TabItem>
<TabItem label="VirtualBox">
<Steps>
1. Open the **Snapshots** panel for the VM.
2. Right-click `pre-change-1` and choose **Restore**.
3. Uncheck **Create snapshot of current state** and click **Restore**.
</Steps>
</TabItem>
</Tabs>

Start the VM and verify recovery:

```bash
sudo systemctl status ssh
sudo sshd -T 2>&1 | head -3
tail -5 /etc/ssh/sshd_config
```

All three should be clean: SSH active, no config error, no `INVALID_VALUE` line.

<Aside type="caution">
Snapshots are not backups. The snapshot and the base disk share the same storage pool. If the host machine's disk fails, both are lost. Backups must reside on separate storage.
</Aside>

### Delete the Snapshot

Once recovery is confirmed, delete `pre-change-1`:

<Tabs>
<TabItem label="UTM">
<Steps>
1. Right-click the VM and select **Snapshot > Delete Snapshot**.
2. Select `pre-change-1` and confirm.
</Steps>
</TabItem>
<TabItem label="VirtualBox">
<Steps>
1. Open the **Snapshots** panel.
2. Right-click `pre-change-1` and choose **Delete Snapshot**.
</Steps>
</TabItem>
</Tabs>

<ActivityQuestion>
When you reverted the snapshot, what happened to the delta writes that accumulated between taking the snapshot and reverting? Why does the lecture recommend deleting snapshots once a change is confirmed stable, rather than keeping them indefinitely?
</ActivityQuestion>

## Part 3: Networking Modes

### Observe NAT Behavior

Your VM currently uses NAT.

<Steps>
1. Check the VM's IP address:

   ```bash
   ip addr show
   ```

   Note the address (typically `10.0.2.15` on VirtualBox; varies on UTM).

2. From your **laptop's** terminal (not the VM), try to reach the VM:

   ```bash
   ping -c 3 <vm-ip-address>
   ```

   This will time out on most NAT configurations. The VM can reach outward; nothing can reach in without port forwarding.

3. Confirm the VM still has internet access — run this **inside the VM**:

   ```bash
   ping -c 3 debian.org
   ```
</Steps>

<ActivityQuestion>
The ping from your laptop to the VM times out even though the VM can reach the internet. Explain why, using the lecture's description of how NAT works. What would you need to configure to SSH into the VM from your laptop while it is in NAT mode?
</ActivityQuestion>

### Switch to Host-Only Networking

<Steps>
1. Power off the VM:

   ```bash
   sudo shutdown -h now
   ```

2. Change the network adapter:

   <Tabs>
   <TabItem label="UTM">
   <Steps>
   1. Open **VM Settings > Network**.
   2. Change the mode from **Shared Network** to **Host Only**.
   3. Save and start the VM.
   </Steps>
   </TabItem>
   <TabItem label="VirtualBox">
   <Steps>
   1. Open **Settings > Network > Adapter 1**.
   2. Change **Attached to** from **NAT** to **Host-only Adapter**.
   3. Select `vboxnet0` from the adapter list, then click **OK**.
   4. Start the VM.
   </Steps>
   </TabItem>
   </Tabs>

3. Check the new IP address inside the VM:

   ```bash
   ip addr show
   ```

4. Test reachability from your **laptop**:

   ```bash
   ping -c 3 <new-vm-ip>
   ```

   This should succeed.

5. Test internet access from **inside the VM**:

   ```bash
   ping -c 3 debian.org
   ```

   This will fail: host-only means the host and guest can communicate, but the guest is isolated from the broader network.
</Steps>

### Summary Table

Fill in the table from your observations:

| Mode | Guest can reach internet? | Host can reach guest? | Other LAN machines can reach guest? |
|------|--------------------------|----------------------|--------------------------------------|
| NAT | | | |
| Host-only | | | |

<Aside type="note">
Switch your adapter back to NAT before the next part. Host-only mode breaks internet access, which you will need for package installation.
</Aside>

<ActivityQuestion>
Host-only gave you host-to-guest connectivity but broke internet access. What is present in NAT mode that host-only lacks? If you were setting up multiple VMs that needed to talk to each other but not to the internet, which mode would you use?
</ActivityQuestion>
