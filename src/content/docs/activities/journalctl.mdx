This activity puts into practice the concepts from the [Log Management and Incident Investigation](/lectures/log-management-and-analysis/) lecture. You will build a controlled set of log files on a Linux server, investigate them the way an on-call engineer would using `journalctl`, `grep`, and `awk`, trace a container crash in Kubernetes using `kubectl logs --previous`, and verify a file access event using the kernel audit subsystem. By the end, you will have a timestamped incident timeline backed by evidence from four log sources.

## What You Will Need

- SSH access to an Ubuntu or Debian Linux server where you have `sudo` privileges
- `python3`, `journalctl`, `logger`, `grep`, `awk`, and `logrotate` on that server (all present by default on Ubuntu 22.04)
- `auditd` on the server. Install it if it is not already present:
  ```bash
  sudo apt-get install -y auditd
  sudo systemctl enable auditd --now
  ```
- `kubectl` on your local machine and a running minikube cluster from the [Minikube](/activities/minikube/) activity. Start minikube before class if it is not already running:
  ```bash
  minikube start --driver=docker
  ```
- Two terminals: one SSH'd into the server, one local for `kubectl` commands

## Build the Incident Bundle

Before investigating anything, you need a controlled set of logs to work with. Every student investigates the same failure sequence: a database connection pool exhausted by a long-running export job, causing an order API to return HTTP 500 errors. The journal entries you write in this section are real: `logger` stamps them into the actual systemd journal on your server.

Run the following commands on your **SSH server**.


5. **Create the database host journal excerpt:**

   ```bash
   cat > ~/cs312-log-lab/bundle/db-host-journal.log << 'EOF'

   ```

6. **Create the logrotate config:**

   ```bash
   echo "$HOME/cs312-log-lab/bundle/nginx-access.log {
       size 1k
       rotate 3
       compress
       copytruncate
       missingok
       notifempty
   }" > ~/cs312-log-lab/bundle/logrotate-nginx.conf
   ```

   The config file needs the absolute path to the log file. `$HOME` expands to your home directory so the path is correct regardless of username.

7. **Confirm all five files exist:**

   ```bash
   ls -1 ~/cs312-log-lab/bundle
   ```

   You should see `db-host-journal.log`, `logrotate-nginx.conf`, `nginx-access.log`, `order-api.jsonl`, and `postgres.log`.

8. **Write real journal entries on your server:**

   ```bash
   logger -t cs312-log-lab "incident bundle ready for $(whoami) on $(hostname)"
   logger -p user.warning -t cs312-log-lab "practice warning: the 5xx spike begins at 03:04 UTC"
   ```

   `logger` sends messages directly to the systemd journal, tagged with the program name `cs312-log-lab`.

9. **Query the entries you just wrote:**

   ```bash
   journalctl -t cs312-log-lab --since "5 minutes ago" --no-pager
   ```

   The `-t` flag filters by syslog identifier. The journal indexes entries by identifier, priority, and timestamp, so this filter runs in constant time regardless of how large the journal is.

10. **Filter on priority:**

   ```bash
   journalctl -t cs312-log-lab -p warning --since "5 minutes ago" --no-pager
   ```

   Only the warning-level entry appears. The info-level entry is gone. Severity is stored as structured metadata, so this filter never requires scanning message text.

11. **Check the boot history:**

    ```bash
    journalctl --list-boots | head -5
    ```

    Boot boundaries are indexed in the journal. When an incident spans a reboot, `journalctl -b -1` jumps directly to the previous boot without requiring a timestamp range.

</Steps>

## Scope the Symptom from the Edge

Start where the user-facing symptom is visible. The web server access log is close to the customer experience, so it is the fastest place to see when the failure became visible and how abruptly it started.

<Steps>

1. **Pull out the key fields from the access log:**

   ```bash
   awk '{print $1, $4, $7, $9}' ~/cs312-log-lab/bundle/nginx-access.log
   ```

   This prints client IP, timestamp, request path, and HTTP status code. Notice how much operational meaning is packed into one line: source, time, target, and outcome.

2. **Count 5xx responses by minute:**

   ```bash
   awk '$9 >= 500 {print $4}' ~/cs312-log-lab/bundle/nginx-access.log \
     | cut -d: -f1-3 | sort | uniq -c
   ```

   You should see no errors before `03:04`, then a sudden jump. Converting a wall of log lines into a per-minute count is often the fastest way to find when a pattern began.

3. **Narrow to the exact minute where failures begin:**

   ```bash
   grep -E '03:04:[0-9]{2}.*" 500 ' ~/cs312-log-lab/bundle/nginx-access.log
   ```

   This regex keeps the search focused on one minute and one HTTP status class. In a real incident, narrowing like this prevents you from reading thousands of irrelevant lines.

4. **Filter health-check noise to see only customer traffic:**

   ```bash
   grep -v 'GET /healthz' ~/cs312-log-lab/bundle/nginx-access.log
   ```

   Health checks matter operationally, but they are not the customer path you are investigating right now. Remove the noise first, then bring it back if it becomes relevant.

</Steps>

## Broaden Across the Application and Database

The web log tells you requests are failing. The next step is to move one layer inward and find what dependency failed first.

<Steps>

1. **Show only the application's error and fatal entries:**

   ```bash
   grep -E '"level":"(error|fatal)"' ~/cs312-log-lab/bundle/order-api.jsonl
   ```

   This file uses structured JSON logging. Each field is named, so filtering on `"level"` works without touching the message text.

2. **Extract the dependency fields from those entries:**

   ```bash
   grep -E '"level":"(error|fatal)"' ~/cs312-log-lab/bundle/order-api.jsonl \
     | grep -oE '"upstream_host":"[^"]+"|"upstream_port":[0-9]+|"duration_ms":[0-9]+'
   ```

   The repeated host, port, and 30-second duration values show the same dependency failing each time, not a transient random error.

3. **Search the database log for the matching failure window:**

   ```bash
   grep -Ei 'fatal|remaining connection slots|error' ~/cs312-log-lab/bundle/postgres.log
   ```

   PostgreSQL ran out of connection slots. This is the immediate cause of the application timeouts.

4. **Check the node-level journal excerpt around the same time:**

   ```bash
   grep -Ei 'export|connection|postgres' ~/cs312-log-lab/bundle/db-host-journal.log
   ```

   The database host's own log shows a long-running export job opening 90 database sessions more than two minutes before the first application timeout appears. This is the step that moves from immediate cause to root cause.

5. **Compare the two log formats side by side:**

   ```bash
   head -2 ~/cs312-log-lab/bundle/order-api.jsonl
   head -2 ~/cs312-log-lab/bundle/db-host-journal.log
   ```

   The JSON line is easier to parse programmatically because every field is named. The syslog-style line is easier to scan at a glance in a terminal. Both formats are common in production, often from the same application stack.

</Steps>

## Trace a Crash in Kubernetes

In containerized environments, the current container log is often not the one that contains the crash. This section uses your local minikube cluster to practice the investigation commands before you need them in a real incident.

Switch to your **local machine terminal** for this section.

<Steps>

1. **Make sure minikube is running:**

   ```bash
   minikube status
   ```

   If the cluster is stopped:

   ```bash
   minikube start --driver=docker
   ```

2. **Deploy a pod that prints errors and then exits:**

   ```bash
   kubectl apply -f - <<'EOF'
   apiVersion: v1
   kind: Pod
   metadata:
     name: crash-demo
   spec:
     restartPolicy: OnFailure
     containers:
     - name: crash-demo
       image: busybox:1.36
       command:
       - sh
       - -c
       - |
         echo "INFO starting crash-demo pid=1"
         echo "INFO listening on :8080"
         echo "INFO readiness probe succeeded"
         sleep 5
         echo "ERROR database connection timeout host=postgres-prod port=5432 request_id=req-9001"
         echo "FATAL panic: unable to start HTTP server because dependency check failed"
         exit 1
   EOF
   ```

   The container prints startup messages that look healthy, waits five seconds, then logs the error and exits with a non-zero code.

3. **Watch the pod move through its lifecycle:**

   ```bash
   kubectl get pod crash-demo -w
   ```

   You will see it move through `Pending`, `Running`, `Error`, and after several restarts, `CrashLoopBackOff`. Press Ctrl+C when you see the backoff status appear.

4. **Read the current container's log:**

   ```bash
   kubectl logs crash-demo
   ```

   You see the most recently started container's output. In a real incident, this container might look completely healthy because Kubernetes restarted it fresh after the crash. The evidence you need is in the previous container.

5. **Read the previous container's log:**

   ```bash
   kubectl logs crash-demo --previous
   ```

   `--previous` retrieves the log from the terminated container that ran before the current one. When a container crashes and restarts, the new container writes to a new log stream. Without `--previous`, the crash evidence disappears behind the fresh startup.

6. **Inspect the cluster's view of what happened:**

   ```bash
   kubectl describe pod crash-demo
   ```

   Scroll to the `Events` section at the bottom. You will see `Started`, `BackOff`, and `Unhealthy` entries. These are control-plane events from the kubelet and scheduler, not from the application. A failed image pull, an OOM kill, or a readiness probe failure all appear here before any application log exists.

7. **Clean up:**

   ```bash
   kubectl delete pod crash-demo
   ```

</Steps>

## Check the Audit Trail

Switch back to your **SSH server terminal**. The kernel audit subsystem records file accesses and privilege escalations at the system-call level, regardless of whether any application has been configured to log them.

<Steps>

1. **Confirm auditd is running:**

   ```bash
   sudo systemctl status auditd --no-pager
   ```

   The status should show `active (running)`. If it shows `inactive`, run `sudo systemctl start auditd` before continuing.

2. **See a summary of recent audit activity:**

   ```bash
   sudo aureport --summary
   ```

   `aureport` reads `/var/log/audit/audit.log` and produces category totals: logins, file accesses, executions, and more. The audit subsystem has been recording events since the daemon started, with no application involvement.

3. **Add a temporary watch rule on one of the bundle files:**

   ```bash
   AUDIT_FILE="$HOME/cs312-log-lab/bundle/order-api.jsonl"
   sudo auditctl -w "$AUDIT_FILE" -p r -k cs312-audit
   ```

   `-w` specifies the file to watch, `-p r` watches for read access, and `-k` sets a search key so you can find these events later. This rule is active until the next reboot or until you remove it explicitly.

4. **Trigger the rule by reading the file:**

   ```bash
   grep '"level":"fatal"' "$AUDIT_FILE" > /dev/null
   sleep 1
   ```

   Your `grep` command read the file. The audit subsystem recorded that read at the kernel level regardless of whether `grep` itself does any logging.

5. **Search for the audit event:**

   ```bash
   sudo ausearch -k cs312-audit --start recent
   ```

   The audit record shows the file path, the process that accessed it, the real user ID, and the timestamp. This is the kind of evidence that appears in compliance audits and security investigations: what accessed this file, and when.

6. **Remove the watch rule:**

   ```bash
   sudo auditctl -W "$AUDIT_FILE" -p r -k cs312-audit
   ```

   `-W` (capital W) removes the specific watch. The audit log entry you just created remains in `/var/log/audit/audit.log` even after the rule is removed.

</Steps>

## Rotate the Log

Before writing up the incident, confirm that the evidence is still accessible after rotation. A busy web server rotates its access log daily, so evidence from earlier in an incident may live in a compressed archive.

<Steps>

1. **Check the access log size before rotation:**

   ```bash
   wc -l -c ~/cs312-log-lab/bundle/nginx-access.log
   ```

   The line count is the evidence count. The byte count is what the rotation policy measures.

2. **Force a rotation using the prepared config file:**

   ```bash
   logrotate -f \
     -s ~/cs312-log-lab/bundle/logrotate.status \
     ~/cs312-log-lab/bundle/logrotate-nginx.conf
   ```

   `-f` forces rotation regardless of size. `-s` keeps the state file in your working directory instead of the system default location.

3. **Verify the rotated archive and the truncated active file:**

   ```bash
   ls -lh ~/cs312-log-lab/bundle/nginx-access.log*
   ```

   You should see a compressed archive alongside a much smaller active file. `copytruncate` in the config means the running process (Nginx in production) could keep writing to the original path without interruption.

4. **Read the archived evidence:**

   ```bash
   zcat -f ~/cs312-log-lab/bundle/nginx-access.log.1* | tail -5
   ```

   Compression changes the storage format, not the content. The 500 entries you investigated earlier are still readable. The `-f` flag handles both `.gz` and uncompressed files.

</Steps>

<Aside type="note" title="Rotation solves size; shipping solves ephemerality">
Log rotation keeps disk usage bounded on a server that is always running. It does not help when a pod is deleted: container log files in `/var/log/pods/` are removed with the pod. In production, a DaemonSet agent like Fluent Bit reads container log files on the node and forwards them to a durable store before the pod disappears. That is the gap that centralized log shipping closes, and the reason the lecture distinguishes between local rotation and the centralized collection pipeline.
</Aside>

## Write the Incident Timeline

At some point you stop searching and write down what happened. The timeline table integrates evidence from multiple sources into a single artifact that makes the causal chain explicit.

<Steps>

1. **Set your name in a shell variable. Replace `YOUR NAME` with your actual name:**

   ```bash
   export CS312_NAME="YOUR NAME"
   ```

2. **Create the timeline file:**

   ```bash
   cat <<EOF > ~/cs312-log-lab/timeline.txt
   Investigator: ${CS312_NAME}
   Host: $(hostname)
   Generated: $(date -u +%FT%TZ)

   Incident: order-api HTTP 500 spike (15 Mar 2026 starting 03:04 UTC)
   Root cause: nightly-export.service held 90 long-lived PostgreSQL connections,
   exhausting the connection pool and preventing order-api from connecting.

   TIME (UTC)   SOURCE               EVENT
   02:58:23     db-host-journal.log  nightly-export.service started, opened 90 sessions
   03:01:04     postgres.log         connection slots exhausted (FATAL)
   03:01:17     order-api.jsonl      first database timeout (req-1002, 30012ms)
   03:03:58     order-api.jsonl      connection pool exhausted, retrying (req-1004)
   03:04:01     nginx-access.log     HTTP 500 errors begin on /api/orders
   03:04:12     order-api.jsonl      startup dependency check FATAL after restart (req-1006)
   EOF
   ```

3. **Print the timeline:**

   ```bash
   cat ~/cs312-log-lab/timeline.txt
   ```

   Your name, hostname, and cause chain should all appear in one clean block. Notice the gap between root cause (03:01:04) and first user-visible symptom (03:04:01): three minutes during which the application was degrading before requests started failing. That gap is the MTTD if alerting fires at 03:04.

</Steps>

## Going Further

You now have the core investigation loop: scope the symptom, narrow the time window, broaden across adjacent sources, and write up the cause chain. The prepared bundle gave you a controlled version of that loop. The natural next step is to run the same process against real data.

If you still have a web service running from an earlier course activity, repeat this workflow on live data. Use `journalctl -u <service> -p err --since "1 hour ago"`, inspect the matching files in `/var/log`, and compare timestamps to what your service was doing at that time. The same three phases apply: scope, narrow, broaden.

For deeper log parsing, install `jq` on your server and rewrite the JSON investigation steps from the "Broaden" section using `jq` rather than `grep -oE`. `jq` extracts fields structurally without text matching, so a filter like `jq 'select(.duration_ms > 5000)'` works on any JSON log file where that field exists, regardless of the surrounding structure. That is the next step up from ad-hoc terminal searching toward a repeatable toolkit.

For centralized log search, the [Loki getting-started guide](https://grafana.com/docs/loki/latest/getting-started/) walks you through deploying a minimal Loki instance and querying it with LogQL. The label-first query model from the lecture becomes concrete when you run a real query: start with the stream selector `{service="order-api"}` to narrow by label, then chain `|= "database connection timeout"` to filter by message content. Comparing query speed between a wide label selector and a narrow one shows the cost tradeoff that Loki's architecture makes.
