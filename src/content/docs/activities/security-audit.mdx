This activity puts into practice the concepts from the [System Security and Hardening](/lectures/system-security-and-hardening/) lecture. You will apply the Linux hardening checklist to a real server: configure SSH key authentication, close unnecessary ports with a default-deny firewall, install and configure Fail2Ban, and create a least-privilege deploy user. By the end, you will have a server whose attack surface is substantially smaller than the default Ubuntu configuration, and you will be able to describe what each change closes and why it matters.

## What You Will Need

- An EC2 instance running Ubuntu 22.04 or 24.04 that you can SSH into (your instance from a prior lab works fine)
- Your local SSH keypair, or the ability to generate one (`ssh-keygen` is available on macOS, Linux, and Windows 10+)
- A terminal on your local machine with SSH access to the instance
- The instance's public IP address

---

## Part 1: Inspect the Current State

Before hardening anything, document what the server looks like right now. The goal is to establish a baseline: what is listening, who can log in, and what the SSH configuration currently allows. You will compare against this at the end.

<Steps>

1. **Connect to your instance:**

   ```bash
   ssh ubuntu@YOUR_INSTANCE_IP
   ```

   You should land at a prompt showing your username and hostname, something like `ubuntu@ip-172-31-4-23:~$`. Note both — you will use the hostname later.

2. **Check what services are listening on the network:**

   ```bash
   ss -tlnp
   ```

   `ss` is the modern replacement for `netstat`. The flags mean: `-t` TCP only, `-l` listening sockets only, `-n` numeric addresses (no DNS lookups), `-p` show the process name. You will see at minimum `sshd` on port 22. On a fresh instance you may also see `systemd-resolved` on `127.0.0.53` (local DNS) and nothing else. Make a note of every entry and its port.

3. **Check the current SSH configuration:**

   ```bash
   sudo sshd -T | grep -E "passwordauthentication|permitrootlogin|allowusers|pubkeyauthentication"
   ```

   `sshd -T` prints the effective sshd configuration after all includes and defaults are resolved. This is more reliable than reading `sshd_config` directly because it shows the actual values in use. On a default AWS Ubuntu instance you will typically see `passwordauthentication no` (Amazon disables it by default) and `permitrootlogin prohibit-password`. Note all four values — you will change at least two of them.

4. **List human login accounts:**

   ```bash
   grep -v nologin /etc/passwd | grep -v false | grep -v sync
   ```

   The `-v` flag inverts the match: instead of showing lines that contain the pattern, it shows lines that do not contain it. Each pipe removes another category of system accounts: accounts whose shell is `/usr/sbin/nologin` cannot open an interactive session; those with `/bin/false` as the shell immediately exit on login; `sync` is a special utility account. What remains are accounts with a real shell that a person could actually log in with. On a fresh Ubuntu instance you will typically see `root` and `ubuntu`. Note the list.

5. **Check recent login history and failures:**

   ```bash
   last -n 10
   sudo lastb -n 10 2>/dev/null
   ```

   `last` shows successful logins from `/var/log/wtmp`. `lastb` shows failed login attempts from `/var/log/btmp`. On a new instance `lastb` may be empty or may already show automated scan attempts if the instance has been up for more than a few hours.

</Steps>

## Part 2: Set Up SSH Key Authentication

AWS EC2 instances use key pairs for the initial login, which means you already have a key. This section ensures key-based auth is configured correctly and adds a dedicated deploy user whose permissions you will control explicitly.

<Steps>

1. **Verify your key-based login is working.** Before making any changes, open a second terminal and confirm you can SSH in again with your current key:

   ```bash
   ssh -i ~/.ssh/your-key.pem ubuntu@YOUR_INSTANCE_IP
   ```

   Keep this second session open for the rest of Part 2. If a configuration change locks you out, you have a recovery session already in place.

2. **Create a dedicated deploy user:**

   ```bash
   sudo adduser deploy
   sudo usermod -aG sudo deploy
   ```

   `adduser` creates the account, home directory, and default shell. In `usermod -aG sudo deploy`, the `-a` flag means append: it adds the new group to the account's existing group memberships without removing any. Without `-a`, `-G` would replace all supplementary groups, potentially locking the account out of other permissions. The `-G sudo` argument names the group to add. This user is what you would use for application management instead of `ubuntu`.

3. **Add your public key to the deploy user's authorized keys:**

   ```bash
   sudo mkdir -p /home/deploy/.ssh
   sudo cp ~/.ssh/authorized_keys /home/deploy/.ssh/
   sudo chown -R deploy:deploy /home/deploy/.ssh
   sudo chmod 700 /home/deploy/.ssh
   sudo chmod 600 /home/deploy/.ssh/authorized_keys
   ```

   `authorized_keys` is the file sshd reads to determine which public keys are permitted to authenticate for an account. Each line is one public key. When you connect with SSH, the server checks whether your private key matches any public key in this file; if it does, authentication succeeds without a password. You are copying the same public key that lets you log in as `ubuntu` to the `deploy` account. The `700` and `600` permissions are required by sshd: if the `.ssh` directory or `authorized_keys` file is readable by others, sshd rejects it for security reasons.

4. **Test the deploy login from your second terminal:**

   ```bash
   ssh -i ~/.ssh/your-key.pem deploy@YOUR_INSTANCE_IP
   ```

   You should land at a `deploy@hostname` prompt. If this does not work, do not proceed to the next step — the sshd_config changes below will restrict logins.

5. **Harden `sshd_config`:**

   ```bash
   sudo nano /etc/ssh/sshd_config
   ```

   Find or add these four directives. If a line exists with a different value, change it. If it is commented out with `#`, uncomment and set it:

   ```text
   PasswordAuthentication no
   PermitRootLogin no
   PubkeyAuthentication yes
   AllowUsers deploy
   ```

   Save and exit (`Ctrl+X`, `Y`, `Enter` in nano).

6. **Restart sshd and verify — without closing your current session:**

   ```bash
   sudo systemctl restart sshd
   sudo sshd -T | grep -E "passwordauthentication|permitrootlogin|allowusers|pubkeyauthentication"
   ```

   The output should now show `allowusers deploy`. From your second terminal, confirm that `ssh -i ~/.ssh/your-key.pem deploy@YOUR_INSTANCE_IP` still works. Also confirm that `ssh -i ~/.ssh/your-key.pem ubuntu@YOUR_INSTANCE_IP` is now rejected — the `AllowUsers deploy` directive means sshd rejects any user not on the list, regardless of whether they have a valid key.

</Steps>

<Aside type="caution" title="Do not close the first session until the second works">
If you close your only SSH session before verifying that `deploy` can log in with the new configuration, you may need to use the EC2 Instance Connect console or an AWS Systems Manager Session Manager to recover. Keep both sessions open until you have confirmed key-based login as `deploy`.
</Aside>

## Part 3: Configure the Firewall

With SSH secured, you will configure UFW (Uncomplicated Firewall) to default-deny all inbound traffic and explicitly allow only the ports this server needs.

<Steps>

1. **Set the default policies:**

   ```bash
   sudo ufw default deny incoming
   sudo ufw default allow outgoing
   ```

   This does not activate the firewall yet. You are staging the rules first so there is no moment where the firewall is active but SSH is not yet allowed.

2. **Allow SSH with rate limiting:**

   ```bash
   sudo ufw limit 22/tcp
   ```

   The `limit` rule allows up to six connection attempts from a single IP within 30 seconds, then blocks that IP temporarily. It is a lighter version of Fail2Ban that works at the network level rather than the application log level.

3. **Allow web traffic (add only the ports your server actually uses):**

   ```bash
   sudo ufw allow 80/tcp
   sudo ufw allow 443/tcp
   ```

   Port 80 is HTTP (unencrypted web traffic) and port 443 is HTTPS (TLS-encrypted web traffic). If your server does not serve web traffic, skip these. Only open ports for services that are actually running.

4. **Enable the firewall and verify:**

   ```bash
   sudo ufw enable
   sudo ufw status verbose
   ```

   The output should show:

   ```
   Status: active
   Default: deny (incoming), allow (outgoing), disabled (routed)

   To                         Action      From
   --                         ------      ----
   22/tcp                     LIMIT IN    Anywhere
   80/tcp                     ALLOW IN    Anywhere
   443/tcp                    ALLOW IN    Anywhere
   ```

   If you see this and your SSH session is still active, the firewall is correctly configured.

5. **Confirm the port state from inside the server:**

   ```bash
   ss -tlnp
   ```

   Compare this output to the list you made in Part 1. Every port that is now visible here should correspond to a UFW allow rule. Any port that is listening but not in the allow list is still reachable within the VPC but blocked from the internet.

</Steps>

## Part 4: Install and Configure Fail2Ban

UFW's rate-limiting rule blocks raw connection attempts. Fail2Ban goes a step further: it reads application logs, identifies failed authentication patterns, and dynamically bans the source IP via a firewall rule.

<Steps>

1. **Install Fail2Ban:**

   ```bash
   sudo apt update
   sudo apt install -y fail2ban
   ```

2. **Create a local configuration file:**

   ```bash
   sudo nano /etc/fail2ban/jail.local
   ```

   Add the following:

   ```ini
   [sshd]
   enabled  = true
   port     = ssh
   filter   = sshd
   backend  = systemd
   maxretry = 5
   findtime = 600
   bantime  = 3600
   banaction = ufw
   ```

   Save and exit. This configures the `sshd` jail: if the same IP fails authentication five times within 600 seconds (10 minutes), it is banned for 3600 seconds (one hour) via a UFW block rule. The `backend = systemd` directive tells Fail2Ban to read from the systemd journal rather than from `/var/log/auth.log` directly, which is the correct source on modern Ubuntu.

3. **Enable and start Fail2Ban:**

   ```bash
   sudo systemctl enable --now fail2ban
   ```

   `enable` registers the service to start at every boot. `--now` starts it immediately. Without `enable`, the service would run this session but not survive a reboot.

4. **Verify the jail is active:**

   ```bash
   sudo fail2ban-client status sshd
   ```

   You should see output like:

   ```
   Status for the jail: sshd
   |- Filter
   |  |- Currently failed: 0
   |  |- Total failed:     0
   |  `- Journal matches: _SYSTEMD_UNIT=sshd.service + _COMM=sshd
   `- Actions
      |- Currently banned: 0
      |- Total banned:     0
      `- Banned IP list:
   ```

   The counts start at zero. If the instance has been receiving scan traffic, you may already see non-zero values in `Total failed`.

</Steps>

<Aside type="tip" title="If you need to unban yourself">
If you accidentally trigger a ban from your own IP address, unban it with: `sudo fail2ban-client set sshd unbanip YOUR.IP.ADDRESS`. To find your current public IP from the server: `curl -s https://ifconfig.me`.
</Aside>

## Part 5: Least-Privilege Sudoers Configuration

The `deploy` user currently has full sudo access. On a production server, application accounts should have only the specific elevated permissions they actually need.

<Steps>

1. **Restrict deploy's sudo access to specific commands:**

   ```bash
   sudo visudo -f /etc/sudoers.d/deploy
   ```

   `visudo` validates the syntax before saving, preventing a broken sudoers file that locks you out of sudo. The `-f` flag creates a new file in `/etc/sudoers.d/` instead of editing the main file.

   Add this single line:

   ```text
   deploy ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx, /usr/bin/systemctl status nginx
   ```

   The rule format is `user host=(run-as) [flags]: command-list`. Reading this one: `deploy` is the user the rule applies to; `ALL` is the host (this machine); `(ALL)` is the user to run as (root in practice); `NOPASSWD:` is the flag that suppresses the password prompt; the command list at the end specifies exactly which executables are allowed, with full paths. Listing full paths prevents a compromised user from putting a malicious binary named `systemctl` earlier in `$PATH`. This grants `deploy` passwordless permission to restart and check nginx, and nothing else. Save and exit.

2. **Verify the restriction works:**

   From your `deploy` session, test that the allowed command succeeds:

   ```bash
   sudo systemctl status nginx
   ```

   Then test that a disallowed command fails:

   ```bash
   sudo apt update
   ```

   You should see `Sorry, user deploy is not allowed to execute '/usr/bin/apt update' as root on hostname.` The restriction is working. A compromised deploy account cannot install software, modify system files, or escalate further.

3. **Inspect the AppArmor profiles in place:**

   ```bash
   sudo aa-status
   ```

   AppArmor is active by default on Ubuntu. The output lists profiles in two modes: **enforce mode** actually blocks operations the profile does not allow; **complain mode** only logs policy violations without blocking them, which is used when testing a new profile before committing to enforcement. Find `sshd` in the list — it should be in enforce mode, which means even if sshd is compromised, the AppArmor profile restricts what files and capabilities it can access, regardless of which user it runs as.

</Steps>

## Part 6: Verify the Hardened State

You have made five distinct changes to this server. This section produces a clean, verifiable summary of the current security configuration.

<Steps>

1. **Confirm the SSH configuration:**

   ```bash
   sudo sshd -T | grep -E "passwordauthentication|permitrootlogin|allowusers|pubkeyauthentication"
   ```

   All four lines should show the hardened values: `passwordauthentication no`, `permitrootlogin no`, `pubkeyauthentication yes`, `allowusers deploy`.

2. **Confirm the firewall rules:**

   ```bash
   sudo ufw status verbose
   ```

3. **Confirm Fail2Ban is running:**

   ```bash
   sudo fail2ban-client status sshd
   ```

4. **Check open ports one final time:**

   ```bash
   ss -tlnp
   ```

   The only ports visible should be ones with corresponding UFW allow rules.

5. **Create a signed verification entry:**

   ```bash
   echo "Hardened by $(whoami) on $(hostname) at $(date)" | sudo tee /var/log/cs312-hardened.log
   cat /var/log/cs312-hardened.log
   ```

   The output will look like:

   ```
   Hardened by deploy on ip-172-31-4-23 at Wed May 27 10:14:32 UTC 2026
   ```

   Your username, your instance hostname, and the timestamp are all in the output. Leave your terminal at this prompt — this screen, showing the full terminal with the verification entry, is the natural end state of the activity.

</Steps>

## Going Further

You have applied the core Linux hardening checklist to a real server. The natural next challenge is to automate what you just did by hand. [Lynis](https://cisofy.com/lynis/) is an open-source security auditing tool that scans a system against hundreds of checks (many drawn from the CIS benchmark) and produces a prioritized hardening report. Run `sudo lynis audit system` and compare its findings against the changes you just made: which of its recommendations did you already address, and which did you miss?

If you want to go deeper into the firewall layer, look at [nftables](https://wiki.nftables.org/wiki-nftables/index.php/Main_Page), the kernel framework that replaced iptables and that UFW uses as its backend. Writing a raw nftables ruleset gives you a much clearer picture of what UFW is doing under the hood, and nftables' unified syntax for IPv4 and IPv6 is a genuine improvement over the old iptables/ip6tables split.
