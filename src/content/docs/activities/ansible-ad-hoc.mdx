This activity puts into practice the concepts from the [Configuration Management with Ansible](/lectures/configuration-management/) lecture. You will connect Ansible to your EC2 instance, run ad-hoc commands to explore and configure the server, and then write a playbook that installs nginx and deploys a custom web page. By the end, you will have a working Ansible workflow from inventory through playbook execution and understand why idempotency matters.

## What You Will Need

- Your EC2 instance from Lab 2, running Ubuntu, with SSH access
- Your `cs312-key.pem` SSH private key file (in your Downloads folder)
- Ansible installed on your **control node** (the machine where you run Ansible commands): see Setup below
- An internet connection (to install packages on the managed node)

## Set Up the Control Node

The **control node** is the machine where you write and run Ansible. It connects to your EC2 instance (the **managed node**) over SSH. Nothing extra needs to be installed on your EC2 instance.

First, move your SSH key to `~/.ssh/` and set its permissions. Then install Ansible for your platform.

## Build Your Inventory

An **inventory** tells Ansible which machines to manage and how to reach them. You will create a minimal INI-format inventory file with your EC2 instance.

Create a file named `hosts.ini` in your working directory with the following content. Replace `<YOUR-EC2-PUBLIC-IP>` with your instance's actual public IP from the EC2 console:

```ini
[managed]
ec2 ansible_host=<YOUR-EC2-PUBLIC-IP> ansible_user=ubuntu

[managed:vars]
ansible_ssh_private_key_file=~/.ssh/cs312-key.pem
ansible_ssh_common_args=-o StrictHostKeyChecking=accept-new
```

The `[managed]` block defines a group named `managed` with one host aliased `ec2`. The `[managed:vars]` block applies variables to every host in that group: `ansible_ssh_private_key_file` points to your key, and `ansible_ssh_common_args` tells SSH to accept the host key automatically on first connection without prompting.

Now test connectivity using the `ping` module:

```bash
ansible -i hosts.ini managed -m ansible.builtin.ping
```

A successful result looks like this:

```
ec2 | SUCCESS => {
    "changed": false,
    "ping": "pong"
}
```

<Aside type="caution" title="If You See UNREACHABLE">
Check that your EC2 instance is running (EC2 console, Instances view), that its security group allows inbound SSH (port 22) from your current IP, and that the path to your key in `hosts.ini` is correct. Test manually with `ssh -i ~/.ssh/cs312-key.pem ubuntu@<YOUR-IP>` to isolate whether the problem is SSH connectivity or Ansible configuration.
</Aside>

## Explore the Managed Node

With connectivity confirmed, you can run ad-hoc commands to inspect the server. Each command uses `-m` to name a module and optionally `-a` to pass arguments.

<Steps>

1. **Gather system facts.** The `setup` module collects information about the managed node: OS version, memory, CPU, network interfaces, and more. The `filter` argument narrows the output:
   ```bash
   ansible -i hosts.ini managed -m ansible.builtin.setup -a "filter=ansible_distribution*"
   ```
   Note the OS name and version. These values are available as variables in every playbook, automatically collected before any task runs.

2. **Check disk usage:**
   ```bash
   ansible -i hosts.ini managed -m ansible.builtin.command -a "df -h /"
   ```
   Notice that the output begins with `"changed": true` even though `df` reads disk usage and changes nothing at all. The `command` module runs a shell command and has no way to determine whether the system changed, so it always reports `changed`.

3. **Create a file with your name.** Replace `YOUR NAME` with your actual name:
   ```bash
   ansible -i hosts.ini managed -m ansible.builtin.copy \
     -a "content='Deployed by: YOUR NAME\n' dest=/tmp/cs312.txt"
   ```
   The output shows `"changed": true` and a green `changed` label.

4. **Read the file back to confirm it was created:**
   ```bash
   ansible -i hosts.ini managed -m ansible.builtin.command -a "cat /tmp/cs312.txt"
   ```
   Your name appears in the `stdout` field.

5. **Run the copy command again, identical to step 3:**
   ```bash
   ansible -i hosts.ini managed -m ansible.builtin.copy \
     -a "content='Deployed by: YOUR NAME\n' dest=/tmp/cs312.txt"
   ```
   This time the output shows `"changed": false` and a yellow `ok` label. The file already exists with exactly that content, so Ansible made no changes.

</Steps>

<ActivityQuestion>
Step 2 showed `"changed": true` for `df -h`, a command that reads nothing and modifies nothing. Step 5 showed `"changed": false` when the file already had the correct content. What is the fundamental difference between the `command` module and the `copy` module that produces this behavior? What does this mean for building automation you can trust?

## Manage Packages Ad-Hoc

The `apt` module manages packages on Debian-based systems. Package management requires root privileges, which Ansible requests with the `--become` flag.

<Steps>

1. **Install the `tree` package:**
   ```bash
   ansible -i hosts.ini managed -m ansible.builtin.apt \
     -a "name=tree state=present update_cache=yes" --become
   ```
   The output shows `"changed": true`.

2. **Verify the installation:**
   ```bash
   ansible -i hosts.ini managed -m ansible.builtin.command -a "tree --version"
   ```

3. **Run the same install command again:**
   ```bash
   ansible -i hosts.ini managed -m ansible.builtin.apt \
     -a "name=tree state=present update_cache=yes" --become
   ```
   This time you should see `"changed": false`. The `apt` module found `tree` already installed at the requested state and did nothing.

4. **Remove the package:**
   ```bash
   ansible -i hosts.ini managed -m ansible.builtin.apt \
     -a "name=tree state=absent" --become
   ```

</Steps>

<Aside type="note" title="The --become Flag">
`--become` tells Ansible to escalate privileges using `sudo` on the managed node. Package management always requires root access. In a playbook, you can set `become: true` at the play level instead of passing `--become` on the command line for each task.
</Aside>

## Your First Playbook

Ad-hoc commands are convenient for exploration, but they are one-off operations: nothing is recorded, reviewed, or repeatable. A **playbook** is a YAML file that describes the desired state of your server and can be committed to version control, reviewed, and re-run safely.

Create a file named `site.yml` in your working directory. Replace `Your Name` with your actual name before saving:

```yaml
---
- name: Configure web server
  hosts: managed
  become: true

  vars:
    student_name: "Your Name"

  tasks:
    - name: Install nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true

    - name: Deploy custom index page
      ansible.builtin.copy:
        content: "<h1>Deployed by {{ student_name }} on {{ ansible_hostname }}</h1>\n"
        dest: /var/www/html/index.html
        owner: www-data
        group: www-data
        mode: "0644"
      notify: Reload nginx

    - name: Ensure nginx is running and enabled
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: Reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded
```

The `{{ student_name }}` placeholder comes from the `vars` block you defined above. The `{{ ansible_hostname }}` placeholder comes from the facts Ansible gathered automatically at the start of the play: this is the same data you saw from the `setup` module in the ad-hoc section.

The `notify: Reload nginx` on the copy task and the `handlers` block work together: if the index page content changes, Ansible schedules the reload to happen at the end of the play. If the page already has the correct content, the handler is skipped entirely.

Run the playbook:

```bash
ansible-playbook -i hosts.ini site.yml
```

You will see a line for each task showing either `changed` (something was modified) or `ok` (already in the desired state). The PLAY RECAP at the bottom summarizes the totals.

<Steps>

1. **Run the playbook a second time:**
   ```bash
   ansible-playbook -i hosts.ini site.yml
   ```
   On this run, every task should show `ok` instead of `changed`, and the `Reload nginx` handler should not appear at all. The server is already in the declared state, so Ansible has nothing to do.

2. **Verify the deployed page from the managed node:**
   ```bash
   ansible -i hosts.ini managed -m ansible.builtin.command -a "curl -s http://localhost/"
   ```
   You should see:
   ```
   <h1>Deployed by Your Name on ip-X-X-X-X</h1>
   ```
   Your name and the EC2 hostname appear in the response.

</Steps>

## Going Further

You have built the core Ansible workflow: inventory, ad-hoc exploration to understand a system, and a playbook with handlers that is safe to re-run. The natural next step is to make playbooks more flexible and reusable.

Jeff Geerling's [Ansible 101 YouTube series](https://www.youtube.com/watch?v=goclfp6a2IQ&list=PL2_OBreMn7FqZkvMYt6ATmgC0KAGGJNAN) starts exactly where this activity ends and walks through variables, templates, and roles with practical examples. Plan an hour or two to work through the first several episodes.

If you prefer to explore specific topics:

- The [Variables guide](https://docs.ansible.com/ansible/latest/playbook_guide/playbooks_variables.html) in the Ansible documentation explains `group_vars` and `host_vars` directories, which let you move variables out of the playbook and into per-group or per-host files: a cleaner structure for managing multiple environments.
- [Roles](https://docs.ansible.com/ansible/latest/playbook_guide/playbooks_reuse_roles.html) package tasks, handlers, templates, and defaults into a reusable directory structure. Once you have written a role for nginx, you can apply it to any inventory with a single line.
- [Ansible Galaxy](https://galaxy.ansible.com/) hosts community-maintained roles. Try installing `geerlingguy.nginx` and applying it, then compare its structure to the nginx task you wrote by hand.
