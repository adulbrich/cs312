This activity puts into practice the concepts from the [Log Management and Incident Investigation](/lectures/log-management-and-analysis/) lecture. You will build a small incident bundle on a Linux server, investigate it the way an on-call engineer would, and compare journal entries, plain-text logs, structured JSON logs, and saved Kubernetes command output. By the end, you will have a short incident summary backed by evidence from each layer of the stack.

## What You Will Need

- SSH access to an Ubuntu or Debian Linux server where you can run commands in your home directory. The EC2 instance from the earlier Prometheus activity is the easiest option if you still have it.
- `journalctl`, `logger`, `grep`, `awk`, `sed`, `sort`, `uniq`, `tail`, `zcat`, and `logrotate` available on that server
- A terminal with copy and paste available
- About 15 MB of free disk space in your home directory

<Aside type="note" title="Why this activity uses a prepared bundle">
Real incidents are messy. For class, you want the same timestamps and the same failure sequence every time. The commands in this activity build a small incident bundle in your home directory so every student investigates the same evidence.
</Aside>

## Build the Incident Bundle

   ```bash
   journalctl -t cs312-log-lab --since "5 minutes ago" --no-pager
   ```

   ```bash
   journalctl --list-boots | head -5
   ```

   This is one of the practical advantages of the journal over a plain text file. Boot boundaries are indexed already, so you can move quickly to "this boot" or "the previous boot" when troubleshooting.

## Scope the Symptom from the Edge

Start where the user-facing symptom is visible. The web server access log is close to the customer experience, so it is the fastest place to see when the failure became visible and how abruptly it started.

<Steps>

1. **Pull out the key fields from the access log:**

   ```bash
   awk '{print $1, $4, $7, $9}' bundle/nginx-access.log
   ```

   This prints the client IP, timestamp, request path, and HTTP status code. Notice how much operational meaning is packed into one log line: source, time, target, and outcome.

2. **Count only the 5xx responses by minute:**

   ```bash
   awk '$9 >= 500 {print $4}' bundle/nginx-access.log | cut -d: -f1-3 | sort | uniq -c
   ```

   You should see no 5xx entries before `03:04`, then a sudden jump. This is the quickest way to turn a wall of lines into a timeline.

3. **Narrow to the exact minute where the failures begin:**

   ```bash
   grep -E '03:04:[0-9]{2}.*" 500 ' bundle/nginx-access.log
   ```

   This regex keeps the search focused on one minute and one outcome. In a real incident, that kind of narrowing is what keeps you from reading thousands of irrelevant lines.

4. **Filter out the health-check noise and look at only customer traffic:**

   ```bash
   grep -v 'GET /healthz' bundle/nginx-access.log
   ```

   Health checks matter operationally, but they are not the customer path you are investigating right now. Remove the noise first, then bring it back later if it becomes relevant.

</Steps>

## Broaden Across the Application and Database

Once the symptom is scoped, move one layer inward. The web server tells you requests are failing; the application and database logs tell you what dependency failed first and where the real bottleneck lives.

<Steps>

1. **Show only the application's error and fatal entries:**

   ```bash
   grep -E '"level":"(error|fatal)"' bundle/order-api.jsonl
   ```

   This file uses structured JSON logging. The timestamps, severity, service name, and other fields are explicit instead of being embedded in one free-form sentence.

2. **Pull out the specific dependency and duration fields from those JSON lines:**

   ```bash
   grep -E '"level":"(error|fatal)"' bundle/order-api.jsonl | grep -oE '"upstream_host":"[^"]+"|"upstream_port":[0-9]+|"duration_ms":[0-9]+'
   ```

   The repeated host and port tell you this is not a random application bug. The same dependency is timing out each time.

3. **Search the database log for the matching failure window:**

   ```bash
   grep -Ei 'fatal|remaining connection slots|error' bundle/postgres.log
   ```

   The PostgreSQL log shows the immediate cause: the server ran out of connection slots.

4. **Check the node-level journal excerpt around the same time:**

   ```bash
   grep -Ei 'export|connection|postgres' bundle/db-host-journal.log
   ```

   This is the step that moves from immediate cause to root cause. The database host's own log shows a long-running export job opening many sessions before the application failures appear.

5. **Read the first line of the JSON log and the first line of the node journal side by side:**

   ```bash
   head -1 bundle/order-api.jsonl
   head -1 bundle/db-host-journal.log
   ```

   The JSON line is easier to parse mechanically because each field is named. The syslog-style line is easier to scan quickly in a terminal. Both formats are common in production.

</Steps>

## Compare Current Logs, Previous Logs, and Events

Container restarts change the shape of log investigation. In Kubernetes, the current container log is often not the one that contains the actual crash. This section uses saved command output so every student sees the same restart sequence without needing a live cluster.

<Aside type="note" title="What these files represent">
`kubectl-logs-current.txt` represents `kubectl logs <pod>`. `kubectl-logs-previous.txt` represents `kubectl logs <pod> --previous`. `kubectl-events.txt` represents the pod's event stream from the control plane.
</Aside>

<Steps>

1. **Read the current container log stream:**

   ```bash
   cat bundle/kubectl-logs-current.txt
   ```

   This log looks healthy because it starts after the restart. If you looked only here, you could easily conclude that nothing useful happened.

2. **Read the previous container log stream:**

   ```bash
   cat bundle/kubectl-logs-previous.txt
   ```

   This is where the real failure appears. The dependency initialization fails, then the process exits.

3. **Search the previous log for the two most important lines:**

   ```bash
   grep -nE 'database|FATAL|panic' bundle/kubectl-logs-previous.txt
   ```

   These are the lines you would quote in an incident channel because they connect the restart to a specific dependency failure.

4. **Search the Kubernetes event stream for cluster-level context:**

   ```bash
   grep -nE 'BackOff|Unhealthy|Started|Created' bundle/kubectl-events.txt
   ```

   Events show what the control plane and kubelet observed: container creation, startup, failed readiness, and restart backoff. They do not replace the application log. They complement it.

</Steps>

<ActivityQuestion>
If you had only the current log and the event stream, what important detail would still be missing? Why do the event stream and the previous log answer different questions?
</ActivityQuestion>

## Rotate the Log and Inspect the Collection Path

An incident response mindset is not enough by itself. Logs have to survive long enough to investigate, and in container environments they need to be shipped off the node before the pod disappears.

<Steps>

1. **Check the size of the access log before rotation:**

   ```bash
   wc -l -c bundle/nginx-access.log
   ```

   The line count tells you how much evidence is in the file. The byte count matters because rotation policies trigger on size, time, or both.

2. **Force a rotation using the prepared config file:**

   ```bash
   logrotate -f -s bundle/logrotate.status bundle/logrotate-nginx.conf
   ```

   `-f` forces rotation even in a lab, and `-s` keeps the state file in your working directory instead of the system default location.

3. **Verify that the rotated file exists and the active file was truncated:**

   ```bash
   ls -l bundle/nginx-access.log*
   ```

   You should see a new compressed archive and a much smaller active log file. That is the operational goal: keep the service writing to a fresh file while preserving the old data.

4. **Read the archived copy to prove the evidence is still there:**

   ```bash
   zcat -f bundle/nginx-access.log.1.gz | tail -n 5
   ```

   Compression changes the storage format, not the investigative value.

5. **Inspect the Fluent Bit collection config and the sample LogQL query:**

   ```bash
   grep -E 'Path|Parser|Host|Port|Labels' bundle/fluent-bit.conf
   cat bundle/logql-query.txt
   ```

   The Fluent Bit config shows where a node-level agent reads pod logs and which labels it forwards. The LogQL query shows how those labels become the starting point for centralized searching later.

</Steps>

## Write the Incident Summary

At some point you stop searching and write down what happened. This section produces a clean artifact that captures the symptom, the cause chain, and the specific lines that support your conclusion.

<Steps>

1. **Set your name in a shell variable. Replace `YOUR NAME` with your actual name:**

   ```bash
   export CS312_NAME="YOUR NAME"
   ```

2. **Create the summary file from the evidence you just collected:**

   ```bash
   cat <<EOF > incident-summary.txt
   Investigator: ${CS312_NAME}
   Host: $(hostname)
   Prepared at: $(date -u +%FT%TZ)
   Symptom: HTTP 500 spike began at 03:04 UTC in nginx-access.log
   Immediate cause: order-api timed out connecting to postgres-prod:5432
   Root cause: nightly-export.service opened too many PostgreSQL sessions on db-prod-01
   Supporting application log: $(grep -m1 'database connection timeout' bundle/order-api.jsonl)
   Supporting database log: $(grep -m1 'remaining connection slots' bundle/postgres.log)
   Supporting cluster event: $(grep -m1 'BackOff' bundle/kubectl-events.txt)
   Loki-style query: {namespace="default",pod="order-api-7d9f6cdb5c-abc12",container="order-api"} |= "database connection timeout"
   EOF
   ```

   This is the point of the investigation: a short, defensible statement of what failed and why.

3. **Print the summary in the terminal:**

   ```bash
   cat incident-summary.txt
   ```

   Your name, host, and cause chain should all be visible in one clean block of output.

</Steps>

## Going Further

You now have the core investigation loop: scope the symptom, narrow the time window, and broaden across adjacent sources until the root cause is defensible. The natural next step is to run the same process against a real service instead of a prepared bundle.

If you still have a web server or application running from an earlier course activity, repeat this workflow on live data: use `journalctl -u <service> -p err --since "30 minutes ago"`, inspect the matching files in `/var/log`, and compare the timestamps to what your service was doing at the time. If you have access to a cluster from later course work, follow the Kubernetes [cluster-level logging architecture](https://kubernetes.io/docs/concepts/cluster-administration/logging/) guide and then add [Fluent Bit](https://docs.fluentbit.io/manual) shipping into [Loki](https://grafana.com/docs/loki/latest/query/) so the same investigation can continue after a pod restart or node replacement.

For a deeper parsing challenge, install `jq` on your server and rewrite part of this activity so the JSON log fields are extracted structurally rather than with regex. That is the next step up from ad-hoc terminal searching: keeping the speed of shell workflows while reducing brittle text matching.
