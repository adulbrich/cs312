The [Arch Linux install activity](/activities/arch-linux-install/) put every layer of a Linux system in your hands during installation. This activity focuses on what comes next: configuring a running system to host services reliably. You will apply concepts from the [Linux Server Planning and Configuration](/lectures/linux-server-planning-and-configuration/) lecture that the install activity did not cover in depth: service accounts, package management, writing systemd unit files, and log and disk monitoring.

<Aside type="tip">
You can use your Arch VM from the previous activity or a fresh Debian or Ubuntu Server VM. You need a regular user with sudo access and a working internet connection from the VM.
</Aside>

## Part 1: Create Service Accounts

**Lecture concept:** This section exercises the *User and Group Management* concepts from the lecture, specifically service accounts vs. login accounts and the principle of least privilege.

A service account owns the process running your application. It has no login shell (so attackers who exploit the service cannot use it to log in interactively) and typically no home directory. Creating it with `useradd -r` marks it as a system account (UID below 1000).

### Create an Application Service Account

<Tabs>
<TabItem label="Arch">
<Steps>
1. Create the service account:

   ```bash
   sudo useradd -r -s /usr/bin/nologin -M webapp
   ```

   The flags do the following: `-r` creates a system account with a UID below 1000, `-s /usr/bin/nologin` sets a shell that immediately exits to prevent interactive login, and `-M` skips creating a home directory.

2. Verify the account was created:

   ```bash
   getent passwd webapp
   id webapp
   ```

   Confirm that the UID shown by `id webapp` is below 1000.
</Steps>
</TabItem>
<TabItem label="Debian / Ubuntu">
<Steps>
1. Create the service account:

   ```bash
   sudo useradd -r -s /usr/sbin/nologin -M webapp
   ```

   The flags do the following: `-r` creates a system account with a UID below 1000, `-s /usr/sbin/nologin` sets a shell that immediately exits to prevent interactive login, and `-M` skips creating a home directory.

2. Verify the account was created:

   ```bash
   getent passwd webapp
   id webapp
   ```

   Confirm that the UID shown by `id webapp` is below 1000.
</Steps>
</TabItem>
</Tabs>

### Create a Deploy User

A deploy user is a human-operated account with limited sudo rights used to manage the service without granting full administrator access.

<Steps>
1. Create the account with a home directory and bash shell:

   ```bash
   sudo useradd -m -s /bin/bash deploy
   sudo passwd deploy
   ```

2. Grant scoped sudo access only for the webapp service. Open the sudoers file (never edit it directly):

   ```bash
   sudo visudo
   ```

   Add the following line at the end of the file:

   ```
   deploy ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart webapp.service, /usr/bin/systemctl status webapp.service
   ```

3. Test that the restrictions work:

   ```bash
   su - deploy
   sudo systemctl status webapp.service   # should work
   sudo systemctl restart sshd            # should fail
   exit
   ```
</Steps>

<Aside type="note">
The `su - deploy` command spawns a login shell as the deploy user. The `-` flag loads the deploy user's environment, including the PATH. Without it, the shell inherits your current environment, which can mask permission issues.
</Aside>

## Part 2: Install Packages

**Lecture concept:** This section exercises the *Package Management* section from the lecture. Updating the package index before installing ensures you get the latest available version from your configured repositories.

<Tabs>
<TabItem label="Arch">
<Steps>
1. Synchronize the package database and install nginx:

   ```bash
   sudo pacman -Sy
   sudo pacman -S nginx
   ```

2. Verify the installation:

   ```bash
   nginx -v
   sudo systemctl status nginx
   ```

   Nginx is installed but not yet running; you will control it through systemd in the next part.
</Steps>
</TabItem>
<TabItem label="Debian / Ubuntu">
<Steps>
1. Update the package index and install nginx:

   ```bash
   sudo apt update
   sudo apt install nginx
   ```

2. Verify the installation:

   ```bash
   nginx -v
   sudo systemctl status nginx
   ```

   Nginx is installed but not yet running; you will control it through systemd in the next part.
</Steps>
</TabItem>
</Tabs>

### Inspect the Package

See what files the package installed and where they landed on the filesystem:

<Tabs>

```bash
pacman -Ql nginx | head -20
```
</TabItem>
<TabItem label="Debian / Ubuntu">

The package placed its web root, configuration, and binary in standard FHS locations: `/usr/share/nginx/html` (or `/var/www/html`), `/etc/nginx/`, and `/usr/sbin/nginx`. The package maintainer followed the same filesystem hierarchy standard covered in the lecture.
</Aside>

## Part 3: Write a Custom Systemd Unit

**Lecture concept:** This section exercises the *Systemd Services* section from the lecture: unit files, dependency ordering, restart policy, and logging.

### Create the Application Script

We will write a shell script that simulates a long-running service. This exercises all of the systemd unit file concepts without requiring a full application stack.

<Steps>
1. Create the application directory and script:

   ```bash
   sudo mkdir -p /opt/webapp
   sudo tee /opt/webapp/server.sh << 'EOF'
   #!/bin/bash
   echo "webapp starting on $(hostname) at $(date)"
   while true; do
     echo "webapp: heartbeat $(date +%T)"
     sleep 10
   done
   EOF
   sudo chmod +x /opt/webapp/server.sh
   sudo chown -R webapp:webapp /opt/webapp
   ```

2. Verify the permissions:

   ```bash
   ls -la /opt/webapp/
   ```

   The script should be owned by `webapp:webapp` and executable.
</Steps>

### Write the Unit File

<Steps>
1. Create the systemd unit file:

   ```bash
   sudo tee /etc/systemd/system/webapp.service << 'EOF'
   [Unit]
   Description=Example Web Application
   After=network.target

   [Service]
   Type=simple
   User=webapp
   Group=webapp
   WorkingDirectory=/opt/webapp
   ExecStart=/opt/webapp/server.sh
   Restart=on-failure
   RestartSec=5
   StandardOutput=journal
   StandardError=journal

   [Install]
   WantedBy=multi-user.target
   EOF
   ```

   The three sections do the following: `[Unit]` declares what this service is and its ordering dependency on the network; `[Service]` defines how to run it, including which user to run as, which binary to execute, and how to handle restarts; `[Install]` tells systemd which boot target should include this service.

2. Reload systemd so it picks up the new unit file, then enable and start the service:

   ```bash
   sudo systemctl daemon-reload
   sudo systemctl enable --now webapp.service
   ```

3. Check that the service is running:

   ```bash
   systemctl status webapp.service
   ```

   You should see `active (running)` with recent log output in the status block.
</Steps>

<Aside type="note">
`After=network.target` tells systemd to order this service after network initialization. It does not mean the service will fail if the network is unavailable; for a hard dependency, you would use `Requires=`. The lecture explains this distinction.
</Aside>

## Part 4: Monitor Logs

**Lecture concept:** This section exercises the `journalctl` log inspection tools from the *Systemd Services* section of the lecture.

<Steps>
1. Follow the live log stream:

   ```bash
   sudo journalctl -u webapp.service -f
   ```

   You should see the heartbeat message appear every 10 seconds. Press `Ctrl+C` to stop following.

2. Show the last 20 lines:

   ```bash
   sudo journalctl -u webapp.service -n 20
   ```

3. Filter by time:

   ```bash
   sudo journalctl -u webapp.service --since "5 minutes ago"
   ```
</Steps>

### Test Automatic Restart

<Steps>
1. Kill the script process directly to simulate a crash:

   ```bash
   sudo kill $(pgrep -f server.sh)
   ```

2. Wait 6 seconds, then check the service status:

   ```bash
   systemctl status webapp.service
   ```

   Systemd should have restarted the service automatically because of `Restart=on-failure` and `RestartSec=5`.

3. Check the log for the restart event:

   ```bash
   sudo journalctl -u webapp.service -n 15
   ```

   Look for a line showing `Started`: that is the automatic restart recorded by the journal.
</Steps>

## Part 5: Disk Usage Monitoring

**Lecture concept:** This section exercises the *Filesystem Layout and Disk Management* section from the lecture.

<Steps>
1. Check overall disk usage across all mounted filesystems:

   ```bash
   df -h
   ```

2. Find the largest directories under `/var`, where logs and package caches accumulate:

   ```bash
   sudo du -sh /var/* 2>/dev/null | sort -h | tail -10
   ```

3. Check the systemd journal size specifically:

   ```bash
   sudo journalctl --disk-usage
   ```

4. Trim the journal to 100 MB and confirm the size decreased:

   ```bash
   sudo journalctl --vacuum-size=100M
   sudo journalctl --disk-usage
   ```
</Steps>

## Verify Your Understanding

You have now configured a running Linux system using the same tools and concepts that production sysadmins use daily. Take a moment to reflect on these connections:

| What you did | Lecture section |
|---|---|
| Created `webapp` system account with `useradd -r` | User and Group Management |
| Limited deploy user sudo rights with `visudo` | Privilege Escalation with sudo |
| Installed nginx with `apt install` or `pacman -S` | Package Management |
| Inspected installed file locations with `dpkg -L` or `pacman -Ql` | Filesystem Layout and Disk Management |
| Wrote a `[Unit]`, `[Service]`, `[Install]` unit file | Systemd Services |
| Used `systemctl daemon-reload` and `enable --now` | Systemd Services |
| Followed logs with `journalctl -u -f` | Systemd Services |
| Monitored disk usage with `df -h` and `du -sh` | Filesystem Layout and Disk Management |
| Trimmed journal with `--vacuum-size` | Filesystem Layout and Disk Management |

Consider the following questions:

1. **Service accounts:** Why does the `webapp` service account use `/usr/sbin/nologin` as its shell? What happens if an attacker gains code execution inside the webapp process and tries to run `bash`?
2. **Unit file ordering:** The unit file uses `After=network.target`. Why does a web application need to start after the network? What would you use instead of `network.target` if your service also depends on a running database?
3. **Restart policy:** The unit file uses `Restart=on-failure`. What would `Restart=always` do differently? When would you prefer one over the other?
4. **Disk monitoring:** You found the journal consuming disk space. What other directories would you monitor on a production server that hosts a web application with a database?

## Cleanup

<Steps>
1. Stop and disable the webapp service and remove its unit file:

   ```bash
   sudo systemctl disable --now webapp.service
   sudo rm /etc/systemd/system/webapp.service
   sudo systemctl daemon-reload
   ```

2. Remove the nginx package if desired:

   <Tabs>
   <TabItem label="Arch">
   ```bash
   sudo pacman -Rs nginx
   ```
   </TabItem>
   <TabItem label="Debian / Ubuntu">
   ```bash
   sudo apt purge nginx && sudo apt autoremove
   ```
   </TabItem>
   </Tabs>
</Steps>
