This activity puts into practice the concepts from the [Infrastructure as Code with Terraform](/lectures/infrastructure-as-code/) lecture. You will build a Terraform configuration incrementally: first a single file, then a security group, then outputs, then variables, and finally a planned infrastructure change. By the end, you will have created and destroyed one EC2 instance entirely through code and read the plan and state that explain what Terraform thinks exists.

## What You Will Need

- Terraform 1.6 or newer installed on your laptop ([download](https://developer.hashicorp.com/terraform/install))
- Access to your AWS Academy Learner Lab
- AWS CLI installed
- A text editor
- Your ONID

---

## Start with the Learner Lab and `main.tf`

The first pass is intentionally small. You will refresh the temporary AWS Academy credentials for this session, copy one current Ubuntu AMI ID from the AWS console, and then write one file that launches an EC2 instance from it.

<Steps>

1. **Start the AWS Academy Learner Lab** and wait for it to show as ready.

   Every time the Learner Lab starts, it issues a fresh temporary credential set. Terraform will use whatever credentials the AWS CLI currently has, so this refresh step is not optional.

2. **Open the CLI credentials block** on the Learner Lab page.

   In AWS Academy, click **AWS Details**, then **Show** in the AWS CLI section. You will see a credential block containing an access key ID, secret access key, and session token.

3. **Put those credentials into your default AWS CLI profile:**

   ```bash
   mkdir -p ~/.aws
   vim ~/.aws/credentials
   ```

   Paste the current Learner Lab credentials under the `default` profile:

   ```ini
   [default]
   aws_access_key_id=ASIA...
   aws_secret_access_key=...
   aws_session_token=...
   ```

4. **Check that the fresh credentials work before Terraform touches anything:**

   ```bash
   aws sts get-caller-identity --profile default
   ```

   You should see a JSON response containing your account ID and an ARN. If this command fails, Terraform will fail for the same reason.

5. **Find a current Ubuntu 24.04 AMI ID in the AWS console.**

   Open **EC2 > Instances**, click **Launch instances**, search for **Ubuntu Server 24.04 LTS (64-bit x86)**, and copy the AMI ID shown in the list. You do not need to launch anything from this page.

6. **Create a project directory:**

   ```bash
   mkdir ~/tf-activity && cd ~/tf-activity
   ```

7. **Write `main.tf`:**

   ```hcl
   terraform {
     required_version = ">= 1.6"
     required_providers {
       aws = {
         source  = "hashicorp/aws"
         version = "~> 5.0"
       }
     }
   }

   provider "aws" {
     region = "us-east-1"
   }

   resource "aws_instance" "web" {
     ami           = "REPLACE_WITH_UBUNTU_24_04_AMI_ID"
     instance_type = "t3.micro"

     tags = {
       Name  = "tf-activity-web-YOUR_ONID"
       Owner = "YOUR_ONID"
     }
   }
   ```

8. **Replace the placeholders** in `main.tf`.

   Replace `REPLACE_WITH_UBUNTU_24_04_AMI_ID` with the AMI ID you just copied from the console. Replace `YOUR_ONID` with your actual ONID in both tag values. Do not change anything else yet.

9. **Initialize the working directory:**

   ```bash
   terraform init
   ```

   You will see a new `.terraform/` directory and a `.terraform.lock.hcl` file. Both are expected.

10. **Validate the configuration:**

    ```bash
    terraform validate
    ```

    You should see:

    ```text
    Success! The configuration is valid.
    ```

11. **Read the first plan:**

    ```bash
    terraform plan
    ```

    The output should show one resource to add: `aws_instance.web`.

</Steps>

Terraform can create the EC2 instance, but it cannot invent a valid AMI ID for you. Why did you have to copy that ID from AWS first, and what does that tell you about the difference between values Terraform manages directly and values that must already exist in the cloud platform?

<Aside type="note" title="Why Start This Small?">
This first version still relies on AWS defaults. That is deliberate. The point of the section is to separate Terraform's basic structure from the network details you will add next.
</Aside>

<Aside type="note" title="Finding the AMI Programmatically">
If you already have the AWS CLI configured and want the same AMI ID without using the console, run:

```bash
aws ec2 describe-images \
  --owners 099720109477 \
  --filters "Name=name,Values=ubuntu/images/hvm-ssd/ubuntu-*-24.04-amd64-server-*" \
        "Name=architecture,Values=x86_64" \
        "Name=state,Values=available" \
  --query 'Images | sort_by(@, &CreationDate) | [-1].ImageId' \
  --output text --region us-east-1
```

Here `--owners 099720109477` limits the results to images published by Canonical, the company that publishes Ubuntu. Without that filter, the query could return similarly named images from other publishers. Ubuntu also documents this process in [Find Ubuntu images on AWS](https://documentation.ubuntu.com/aws/aws-how-to/instances/find-ubuntu-images/).

This is useful automation, but the console is the simpler starting point for this activity.
</Aside>

## Add a Security Group

An instance alone is not much of an infrastructure definition. In this section you will add one more AWS object, a security group, and then connect the instance to it so the plan shows a real dependency.

<Steps>

1. **Add the default VPC as a data source** below the provider block in `main.tf`:

   ```hcl
   data "aws_vpc" "default" {
     default = true
   }
   ```

2. **Add a security group** below the instance resource in `main.tf`:

   ```hcl
   resource "aws_security_group" "web" {
     name        = "tf-activity-web-sg-YOUR_ONID"
     description = "Activity web security group"
     vpc_id      = data.aws_vpc.default.id

     ingress {
       description = "HTTP"
       from_port   = 80
       to_port     = 80
       protocol    = "tcp"
       cidr_blocks = ["0.0.0.0/0"]
     }

     egress {
       from_port   = 0
       to_port     = 0
       protocol    = "-1"
       cidr_blocks = ["0.0.0.0/0"]
     }

     tags = {
       Name  = "tf-activity-web-sg-YOUR_ONID"
       Owner = "YOUR_ONID"
     }
   }
   ```

   Replace both `YOUR_ONID` placeholders again.

3. **Attach the security group to the instance** by adding this line inside `aws_instance.web`:

   ```hcl
   vpc_security_group_ids = [aws_security_group.web.id]
   ```

4. **Read the plan again:**

   ```bash
   terraform plan
   ```

   You should now see one data source for the default VPC and two resources to add: the security group and the instance.

5. **Look carefully at the order.** The security group is listed before the instance because the instance block now references `aws_security_group.web.id`. Also notice the difference between the two AWS objects in this file now: Terraform will create the security group, but it only reads the default VPC because that VPC already exists.

</Steps>

<ActivityQuestion>
Which specific line in `main.tf` tells Terraform that the instance depends on the security group? Why is this kind of dependency inference better than manually remembering a creation order yourself?
</ActivityQuestion>

## Ask Terraform for Useful Output

The plan is useful before a change. Outputs are useful after a change. In this section you will add a second file so Terraform prints the values you are most likely to care about after `apply`.

<Steps>

1. **Create `outputs.tf`:**

   ```hcl
   output "instance_id" {
     description = "EC2 instance ID"
     value       = aws_instance.web.id
   }

   output "public_ip" {
     description = "Public IP address"
     value       = aws_instance.web.public_ip
   }

   output "security_group_id" {
     description = "Security group ID"
     value       = aws_security_group.web.id
   }

   output "ami_id" {
     description = "AMI ID configured on the instance"
     value       = aws_instance.web.ami
   }
   ```

2. **Apply the configuration:**

   ```bash
   terraform apply
   ```

   Type `yes` when Terraform asks for confirmation. This creates one security group and one EC2 instance in your AWS account.

3. **Show the outputs explicitly:**

   ```bash
   terraform output
   ```

   You should see the four values you declared in `outputs.tf`, now resolved to real AWS IDs and a public IP.

4. **Read one output by name:**

   ```bash
   terraform output public_ip
   ```

   This prints only the public IP. It is the quickest way to retrieve one value when a script or another tool needs it.

</Steps>

<ActivityQuestion>
Why is `public_ip` a good candidate for an output, while something like every low-level network-interface attribute would be noise? What makes an output useful rather than merely available?
</ActivityQuestion>

<Aside type="caution" title="These Are Real Resources">
Your instance and security group are now live in AWS. Leave the directory alone until you reach the destroy step at the end.
</Aside>

## Turn Hardcoded Values into Variables

The configuration works, but it is rigid. In this section you will add more files and refactor the existing code so the same infrastructure definition is reusable instead of tied to one set of literal strings.

<Steps>

1. **Create `variables.tf`:**

   ```hcl
   variable "onid" {
     description = "Your ONID"
     type        = string
   }

   variable "instance_type" {
     description = "EC2 instance size"
     type        = string
     default     = "t3.micro"
   }
   ```

2. **Create `terraform.tfvars`:**

   ```hcl
   onid = "smithj"
   ```

   Replace `smithj` with your actual ONID.

3. **Add a locals block** in `main.tf` below the default VPC data source:

   ```hcl
   locals {
     common_tags = {
       Owner = var.onid
     }
   }
   ```

4. **Update the security group and instance** so they use variables and locals instead of hardcoded values:

   ```hcl
   resource "aws_security_group" "web" {
     name        = "tf-activity-web-sg-${var.onid}"
     description = "Activity web security group"
     vpc_id      = data.aws_vpc.default.id

     ingress {
       description = "HTTP"
       from_port   = 80
       to_port     = 80
       protocol    = "tcp"
       cidr_blocks = ["0.0.0.0/0"]
     }

     egress {
       from_port   = 0
       to_port     = 0
       protocol    = "-1"
       cidr_blocks = ["0.0.0.0/0"]
     }

     tags = merge(local.common_tags, {
       Name = "tf-activity-web-sg-${var.onid}"
     })
   }

   resource "aws_instance" "web" {
     ami                    = data.aws_ami.ubuntu.id
     instance_type          = var.instance_type
     vpc_security_group_ids = [aws_security_group.web.id]

     tags = merge(local.common_tags, {
       Name = "tf-activity-web-${var.onid}"
     })
   }
   ```

5. **Format and validate the refactor:**

   ```bash
   terraform fmt
   terraform validate
   ```

6. **Read the plan again:**

   ```bash
   terraform plan
   ```

   If your original hardcoded ONID matched the value in `terraform.tfvars`, Terraform should report no infrastructure changes.

</Steps>

<ActivityQuestion>
You just edited multiple files and replaced several literals with references to variables and locals, but Terraform should still report no infrastructure changes. Why? What does that tell you about the difference between refactoring the configuration and changing the infrastructure itself?
</ActivityQuestion>

## Read a Real Change, Inspect State, and Clean Up

Terraform becomes most useful when the configuration and the running infrastructure start to differ. In this final section you will plan a small change, compare the plan with the current state, and then tear everything down cleanly.

<Steps>

1. **Add an instance type override** to `terraform.tfvars`:

   ```hcl
   onid          = "smithj"
   instance_type = "t3.small"
   ```

   Keep your real ONID in place. Only the second line is new.

2. **Read the plan one more time:**

   ```bash
   terraform plan
   ```

   Look for the `~` symbol on `aws_instance.web`. The summary should say Terraform plans to change the instance in place.

3. **List the resources currently recorded in state:**

   ```bash
   terraform state list
   ```

   You should see:

   ```text
   aws_instance.web
   aws_security_group.web
   ```

4. **Inspect the instance state directly:**

   ```bash
   terraform state show aws_instance.web
   ```

   Find the `instance_type` line and the `Owner` tag. The state still reflects the running infrastructure, not the change you only planned.

5. **Destroy everything:**

   ```bash
   terraform destroy
   ```

   Type `yes` when prompted. Terraform removes the instance and security group from AWS.

6. **Confirm the state is empty:**

   ```bash
   terraform state list
   ```

   No output means there are no managed resources left.

</Steps>

<ActivityQuestion>
After you changed `terraform.tfvars`, `terraform plan` showed `t3.small`, but `terraform state show aws_instance.web` still showed the current instance type. Which one represents the desired state and which one represents Terraform's record of the live environment? Why is that distinction essential before you run `apply`?
</ActivityQuestion>

## Going Further

You now have the core Terraform loop in your hands: write, plan, apply, inspect, destroy. If you want one step beyond this activity, keep the scope narrow and extend one idea at a time.

- Save a reviewed plan to a file with `terraform plan -out=tfplan`, then apply that exact reviewed plan with `terraform apply tfplan`. This is the safest path when multiple people need to agree on what will change before it happens.
- Replace the default VPC data source with a different VPC in your account and watch how the plan changes. This is the smallest next step toward managing networking explicitly instead of leaning on AWS defaults.
- Add a remote backend in S3 so state is no longer stored only on your laptop. This is the first step from solo Terraform work toward team-safe Terraform work.
