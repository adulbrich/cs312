Imagine you need to deploy a web server. You log into the AWS console, click through a dozen screens, choose an AMI (Amazon Machine Image, a pre-built OS snapshot used to launch instances), configure a security group, attach a key pair, and launch the instance. A week later a colleague needs an identical server in a different region. Can you reproduce exactly what you did? Probably not with perfect fidelity, and certainly not quickly.

This scenario illustrates the core problem that Infrastructure as Code (IaC) solves. When infrastructure is provisioned by hand, three risks emerge: configuration drift (two servers that should be identical slowly diverge as engineers apply ad-hoc changes to one but not the other), lack of reproducibility (if a disaster strikes, you are relying on memory and wiki pages to rebuild from scratch), and lack of an audit trail (a manual change in a cloud console leaves no pull request, no diff, and no approval record). IaC addresses all three by expressing infrastructure in source files that live in version control. Changes go through code review, environments can be rebuilt from a single command, and drift is detected automatically. Terraform is one of the most widely adopted IaC tools, and the focus of this lecture.

## The Two Phases of Infrastructure Management

It helps to think of infrastructure work in two distinct phases, each with different concerns.

**Initial setup** is the provisioning phase: spinning up servers, configuring networks, creating load balancers, setting up databases. This is largely a one-time activity for a given environment.

**Ongoing maintenance** is the operational phase: updating software versions, deploying new application releases, scaling resources up or down, changing network configuration, and recovering from failures.

The same tools do not always serve both phases equally well. Terraform excels at provisioning and lifecycle management of infrastructure objects. Ansible is better suited for configuration management and application deployment onto already-running servers. CI/CD pipelines handle continuous deployment of application code. In practice, combining tools is common: Terraform provisions an EC2 instance, Ansible installs and configures the application, and GitHub Actions deploys updates automatically. The Configuration Management with Ansible and CI/CD Pipelines lectures cover those tools in depth; this lecture focuses on the provisioning foundation they build on.

## Declarative vs. Imperative Approaches

There are two broad philosophies for automating infrastructure. In an **imperative** approach, you write a sequence of steps: "create a VPC (Virtual Private Cloud, an isolated network you control within AWS), then create a subnet, then launch an instance." Shell scripts and SDK-based tools work this way; the code describes *how* to reach the desired state.

In a **declarative** approach, you describe *what* the desired state looks like: "there should be a VPC with one public subnet and one EC2 instance." The tool figures out how to make reality match the declaration.

Terraform is declarative. You write configuration files that describe the end state of your infrastructure, and Terraform calculates the difference between that desired state and the current state, then applies only the necessary changes. This property is called **convergence**: you can run Terraform repeatedly and it will not recreate resources that already exist and already match the configuration.

<Aside type="tip" title="Declarative Safety">
Declarative tools tend to be safer for teams because the configuration file always represents the intended state. You never have to wonder "which script was run last?"
</Aside>

<HistoricalNote title="Infrastructure as Code Before Terraform (1993-2014)">
Configuration management has older roots than most practitioners realize. CFEngine, written by Mark Burgess in 1993, introduced desired-state convergence, the idea that you describe what a system should look like and the tool reconciles reality with the description, a full decade before Puppet or Chef. Puppet (2005) and Chef (2009) brought the approach to a wider audience but focused on configuring already-running servers. Terraform arrived in 2014, created by Mitchell Hashimoto at HashiCorp with a key insight: the same declarative model that worked for software configuration could be applied to provisioning the infrastructure itself. Terraform's provider model (treating any API as a source of manageable resources) is why a single tool can manage AWS instances, Cloudflare DNS records, GitHub repositories, and Kubernetes objects from the same configuration language.
</HistoricalNote>

## Terraform Architecture

Terraform's design is built around four key concepts.

### Providers

A **provider** is a plugin that teaches Terraform how to talk to a particular platform or service. The AWS provider knows how to create EC2 instances and S3 buckets (Simple Storage Service, AWS's object storage service); the Google Cloud provider knows how to create Compute Engine VMs and Cloud Storage buckets. Providers are distributed independently from Terraform itself through the [Terraform Registry](https://registry.terraform.io/).

### Resources

A **resource** is a single piece of infrastructure managed by a provider: an EC2 instance, a security group, a DNS record, a database. Each resource has a type (like `aws_instance`) and a local name that you choose (like `web`). Together these form the resource address `aws_instance.web`.

### Data Sources

A **data source** lets you look up information that already exists outside of your Terraform configuration. For example, you might query AWS for the latest Ubuntu AMI rather than hard-coding an AMI ID that will go stale. Data sources are read-only; Terraform will never try to create or modify them.

### State

Terraform keeps a record of every resource it manages in a **state file**. This file (by default, `terraform.tfstate` in your working directory) maps the resources in your configuration to real objects in the cloud. State is what allows Terraform to know that `aws_instance.web` corresponds to instance `i-0abc123def456` in your AWS account. State management is important enough to deserve its own section later in this lecture.

## HCL Syntax

Terraform configurations are written in [HashiCorp Configuration Language (HCL)](https://github.com/hashicorp/hcl). HCL is designed to be both human-readable and machine-parseable. The primary building blocks are blocks, variables, outputs, and locals.

### Blocks

Almost everything in HCL is a **block**. A block has a type, zero or more labels, and a body enclosed in curly braces:

```hcl
resource "aws_instance" "web" {
  ami           = "ami-0abcdef1234567890"
  instance_type = "t3.micro"
}
```

Here `resource` is the block type, `"aws_instance"` is the resource type label, and `"web"` is the local name label. Inside the body, `ami` and `instance_type` are **arguments**.

### Variables

Input variables let you parameterize your configuration so that the same code can be reused across environments. You declare a variable in a `variable` block:

```hcl
variable "instance_type" {
  description = "EC2 instance size"
  type        = string
  default     = "t3.micro"
}
```

You then reference it elsewhere as `var.instance_type`. Variables can be set through `.tfvars` files, environment variables, or command-line flags.

### Outputs

Outputs expose values from your configuration so that other tools (or other Terraform configurations) can consume them:

```hcl
output "web_public_ip" {
  description = "Public IP of the web server"
  value       = aws_instance.web.public_ip
}
```

After `terraform apply`, outputs are printed to the terminal and stored in state.

### Locals

Locals are named expressions that let you avoid repeating complex values:

```hcl
locals {
  common_tags = {
    Project     = "cs312"
    Environment = "dev"
  }
}
```

You reference a local as `local.common_tags`. Unlike variables, locals are not settable by the user; they are internal to the configuration.

## A Complete Configuration Example

To see how providers, resources, data sources, variables, outputs, and locals fit together, consider the following configuration. It declares a web server on EC2, backed by a security group that permits SSH from a specified IP and HTTP from anywhere, using the latest Ubuntu 24.04 AMI resolved at plan time rather than a hard-coded ID.

```hcl
terraform {
  required_version = ">= 1.6"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = var.region
}

variable "region" {
  description = "AWS region to deploy into"
  type        = string
  default     = "us-west-2"
}

variable "instance_type" {
  description = "EC2 instance size"
  type        = string
  default     = "t3.micro"
}

variable "ssh_cidr" {
  description = "CIDR block allowed to SSH (e.g., your IP as x.x.x.x/32)"
  type        = string
}

data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"] # Canonical

  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-*-24.04-amd64-server-*"]
  }
}

locals {
  common_tags = {
    Project   = "cs312"
    ManagedBy = "terraform"
  }
}

resource "aws_security_group" "web_sg" {
  name        = "web-sg"
  description = "Allow SSH and HTTP"

  ingress {
    description = "SSH"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = [var.ssh_cidr]
  }

  ingress {
    description = "HTTP"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = local.common_tags
}

resource "aws_instance" "web" {
  ami                    = data.aws_ami.ubuntu.id
  instance_type          = var.instance_type
  vpc_security_group_ids = [aws_security_group.web_sg.id]

  tags = merge(local.common_tags, {
    Name = "cs312-web"
  })
}

output "web_public_ip" {
  description = "Public IP of the web server"
  value       = aws_instance.web.public_ip
}
```

`ssh_cidr` has no default value, so Terraform will prompt for it at plan time or fail in a non-interactive environment unless it is supplied explicitly. This is deliberate: you should never open SSH to `0.0.0.0/0`. The `data "aws_ami"` block looks up the most recent Ubuntu 24.04 AMI owned by Canonical (AWS account `099720109477`), so the configuration never contains a hard-coded AMI ID that would go stale as new images are released.

<Aside type="note" title="AMI IDs Are Region-Specific">
AMI IDs differ across AWS regions. The data source lookup resolves the correct ID for whatever region the provider is configured to use, so this configuration deploys correctly regardless of region without any changes.
</Aside>

## The Core Workflow

Terraform's primary workflow revolves around five commands that you will use on nearly every project.

`terraform init` downloads provider plugins and initializes the working directory. Run it once when you create a new configuration and again whenever you add a new provider or change backend settings. After init, a `.terraform` directory appears containing the downloaded provider binaries, and Terraform writes a `.terraform.lock.hcl` file recording the exact provider versions resolved.

`terraform validate` checks your configuration for syntax errors and internal consistency without contacting any remote API. It is fast and safe to run repeatedly; a good habit is to validate before every plan.

`terraform plan` reads the current state, compares it to the configuration, and produces a detailed execution plan showing exactly what Terraform intends to create, modify, or destroy. Nothing changes in your infrastructure at this stage. Treat the plan output as a code diff: read it carefully before proceeding. You can save a plan to a file with `-out=tfplan` and pass that file directly to `apply`, ensuring that what was reviewed is exactly what gets executed.

`terraform apply` executes the plan. When called without a saved plan file, Terraform displays the plan and asks for confirmation before making any changes. Once confirmed, it provisions resources and updates the state file. When called with a saved plan file (`terraform apply tfplan`), it skips the confirmation prompt because the plan has already been reviewed.

`terraform destroy` removes all resources managed by the configuration. It respects the dependency graph and tears resources down in the correct reverse order, which matters when databases must be removed after the applications that write to them.

A typical session looks like this:

```bash
terraform init
terraform validate
terraform plan -var 'ssh_cidr=203.0.113.50/32' -out=tfplan
terraform apply tfplan
```

When you are done with a temporary environment:

```bash
terraform destroy -var 'ssh_cidr=203.0.113.50/32'
```

One additional command worth keeping in your toolkit is `terraform fmt`, which canonically reformats all `.tf` files in the current directory according to HashiCorp's style conventions. Running it before committing keeps diffs clean and eliminates style noise in code review.

<Aside type="caution" title="Plan Before You Apply">
Always run `terraform plan` before `terraform apply` in any shared or production environment. Treat the plan output as a diff to review carefully, just as you would review a code change before merging.
</Aside>

## State Management

State is one of the most important and most misunderstood aspects of Terraform. The state file records the mapping between your configuration and the real infrastructure, along with metadata such as resource dependencies and attribute values. Without state, Terraform would have no way to know that `aws_instance.web` in your configuration corresponds to a specific running instance in your AWS account.

### Local State

By default, Terraform writes state to a file called `terraform.tfstate` in the project directory. This works fine for individual learning and experimentation, but it creates problems in a team setting. If two engineers run `terraform apply` at the same time from their own laptops, they can overwrite each other's state and corrupt the environment.

### Remote State

For any shared project you should store state in a **remote backend**. AWS S3 with DynamoDB (AWS's managed key-value database, used here for distributed locking) locking is one common pattern:

```hcl
terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "cs312/web/terraform.tfstate"
    region         = "us-west-2"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}
```

With this configuration, state is stored in an S3 bucket (encrypted at rest) and a DynamoDB table provides locking. If one engineer is running `apply`, another engineer who tries to run `apply` at the same time will receive a lock error rather than silently corrupting state.

### Sensitive Data in State

State files contain the attribute values of every managed resource. If a resource has a password attribute, that password is stored in state in plain text. This is why you should always encrypt remote state at rest, restrict access to the state bucket, and never commit `terraform.tfstate` to version control.

<Aside type="caution" title="Never Commit State Files">
Add `*.tfstate` and `*.tfstate.backup` to your `.gitignore` file. State files often contain secrets and should never be committed to a repository.
</Aside>

### Importing Existing Resources

Most teams do not start a Terraform journey with a blank account. You may inherit an EC2 instance, a VPC, or a set of security groups that someone created by hand months ago. The `terraform import` command lets you bring those resources under Terraform management without recreating them.

The workflow has two steps. First, write an empty resource block in your configuration that matches the resource type:

```hcl
resource "aws_security_group" "legacy" {
  # attributes will be populated after import
}
```

Then import the existing resource by its cloud-provider ID:

```bash
terraform import aws_security_group.legacy sg-0abc123def456789
```

Terraform writes the resource's current state into the state file. Running `terraform plan` afterward will show a diff between the (empty) configuration block and the actual attributes. You then fill in the configuration to match the real resource until `terraform plan` reports no changes.

The key limitation is that `terraform import` does not generate the HCL for you. It only updates the state file. You must write the matching configuration yourself. Tools like [terraformer](https://github.com/GoogleCloudPlatform/terraformer) and [opentofu's generate config experiment](https://opentofu.org/docs/language/import/) are beginning to address this gap, but the process still requires careful review.

## Variables and Parameterization

Variables make the same configuration reusable across environments. The range of ways to supply variable values is wider than the basics shown in the HCL syntax section.

### Defaults and Required Variables

A variable with a `default` block is optional; Terraform uses the default if no value is provided. A variable without a default is required; Terraform will prompt for it interactively or fail if running in a non-interactive context such as a CI pipeline.

### Variable Files

For repeatable deployments, you can create a file called `terraform.tfvars` (or any file ending in `.auto.tfvars`):

```hcl
region        = "us-west-2"
instance_type = "t3.small"
ssh_cidr      = "203.0.113.50/32"
```

Terraform loads `terraform.tfvars` automatically. You can also specify a file explicitly with `-var-file`:

```bash
terraform apply -var-file="production.tfvars"
```

This pattern is useful for managing multiple environments (dev, staging, production) from the same configuration with different variable files.

### Variable Types

Terraform supports several types beyond `string`: `number`, `bool`, `list(...)`, `map(...)`, and `object(...)`. For example, to allow multiple SSH CIDRs:

```hcl
variable "ssh_cidrs" {
  description = "CIDR blocks allowed to SSH"
  type        = list(string)
  default     = []
}
```

You would then use `var.ssh_cidrs` in the security group's `cidr_blocks` argument.

## Resource Dependencies

Terraform automatically infers dependencies between resources based on attribute references. When one resource's argument references an attribute of another resource, Terraform records that relationship and ensures the dependency is created first. This is called an **implicit dependency**.

Internally, Terraform builds a **directed acyclic graph (DAG)** of all resources before executing any changes. The DAG captures every dependency relationship, allowing Terraform to determine the correct creation order and to parallelize independent resources. You can observe this parallelism in `terraform apply` output: multiple resources that have no dependency on each other are provisioned simultaneously.

In the configuration shown earlier, `aws_instance.web` references `aws_security_group.web_sg.id`, so Terraform knows it must create the security group before the instance. This is the implicit dependency mechanism at work.

Occasionally you need a dependency that is not visible in the configuration. For example, suppose you have an IAM (Identity and Access Management, AWS's system for controlling who can do what) role that must exist before an instance can assume it, but the instance references the role by name (a string) rather than by Terraform attribute. In this case you can declare an **explicit dependency**:

```hcl
resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = var.instance_type

  depends_on = [aws_iam_role.web_role]
}
```

The `depends_on` argument tells Terraform to create or update `aws_iam_role.web_role` before touching `aws_instance.web`, even though there is no attribute reference linking them.

<Aside type="tip" title="Prefer Implicit Dependencies">
Prefer implicit dependencies through attribute references whenever possible. They are self-documenting: anyone reading the code can see why one resource depends on another. Use `depends_on` only as a last resort.
</Aside>

## Multi-Tier Configuration Patterns

A common cloud infrastructure pattern is a multi-tier architecture: a web tier accessible from the internet, a database tier accessible only from the web tier. The following configuration adds a PostgreSQL database on RDS (Relational Database Service, AWS's managed database offering) alongside the earlier web server. The key detail is in the ingress rule: the database security group permits connections on port 5432 only from the web security group, not from the internet.

```hcl
variable "db_password" {
  description = "Password for the database master user"
  type        = string
  sensitive   = true
}

resource "aws_security_group" "db_sg" {
  name        = "db-sg"
  description = "Allow PostgreSQL from web tier"

  ingress {
    description     = "PostgreSQL from web"
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [aws_security_group.web_sg.id]
  }

  tags = local.common_tags
}

resource "aws_db_instance" "database" {
  identifier          = "cs312-db"
  engine              = "postgres"
  engine_version      = "16"
  instance_class      = "db.t3.micro"
  allocated_storage   = 20
  db_name             = "appdb"
  username            = "dbadmin"
  password            = var.db_password
  skip_final_snapshot = true

  vpc_security_group_ids = [aws_security_group.db_sg.id]

  tags = local.common_tags
}

output "db_endpoint" {
  description = "RDS endpoint for the database"
  value       = aws_db_instance.database.endpoint
}
```

`db_password` is marked `sensitive = true`, which tells Terraform to redact its value from plan and apply output. You would supply it through a `.tfvars` file or the `TF_VAR_db_password` environment variable. Because `aws_security_group.db_sg` references `aws_security_group.web_sg.id`, Terraform infers the full creation order through the dependency graph: web security group, then database security group, then the RDS instance.

## Modules

As configurations grow, repeating the same blocks across projects becomes tedious and error-prone. Terraform **modules** let you package a set of resources into a reusable unit.

A module is simply a directory containing `.tf` files. The directory you have been working in is the **root module**. You can create a child module by placing files in a subdirectory and calling it from the root:

```
project/
  main.tf          # root module
  modules/
    web_server/
      main.tf      # child module
      variables.tf
      outputs.tf
```

The child module `modules/web_server/main.tf` might contain the security group and instance resources, parameterized with variables. The root module calls it like this:

```hcl
module "web" {
  source        = "./modules/web_server"
  instance_type = "t3.micro"
  ssh_cidr      = var.ssh_cidr
}

output "web_ip" {
  value = module.web.public_ip
}
```

Modules enforce a clean interface: the child module declares which variables it accepts and which outputs it exposes. The root module passes values in and reads outputs back. This encapsulation makes it possible to share modules across teams or publish them to the Terraform Registry for the community to use.

<Aside type="tip" title="When to Extract a Module">
A good rule of thumb: if you find yourself copying and pasting a block of resources across projects, it is time to extract a module. Start simple; a module with two or three resources is perfectly fine.
</Aside>

## Other Infrastructure Provisioning Tools

Terraform is not the only tool in this space. The ecosystem includes several alternatives worth knowing.

**OpenTofu** is a community-maintained, open-source fork of Terraform created after HashiCorp changed Terraform's license to the Business Source License in 2023. OpenTofu is a drop-in replacement with identical HCL syntax and is the choice for teams that require a fully open-source license. The two projects are diverging slowly; for most workloads they are interchangeable today.

**Pulumi** lets you write infrastructure definitions in general-purpose programming languages (TypeScript, Python, Go, C#) rather than a domain-specific language like HCL. This lowers the barrier for developers already fluent in those languages and makes it easier to apply standard programming constructs like loops, conditionals, and libraries to infrastructure code.

**AWS CloudFormation** is AWS's native IaC service. It uses JSON or YAML templates and integrates tightly with the AWS ecosystem, but it is cloud-specific. If you are committed to AWS and want first-class integration with Service Control Policies and AWS Config, CloudFormation is worth understanding even if Terraform is your day-to-day tool.

**Azure Resource Manager (ARM) / Bicep** is Microsoft's equivalent for Azure infrastructure. Bicep is a more readable DSL that compiles down to ARM JSON, playing the same role that HCL plays for Terraform.

**Ansible** is primarily a configuration management tool, but it can also provision infrastructure resources through its cloud modules. The overlap with Terraform is real, but the tools approach the problem differently: Ansible is procedural and agent-less; Terraform is declarative and state-driven. They complement each other more than they compete.

<Aside type="tip" title="Tool Combinations">
Many tools overlap in capability without being identical. Terraform plus Ansible is a common pairing: Terraform provisions infrastructure objects, Ansible configures the software running on them. Learning one tool deeply makes learning the others significantly easier, since the underlying concepts (desired state, idempotency, providers, inventory) recur across the whole ecosystem.
</Aside>

## Best Practices

The following practices address the most common sources of pain when using Terraform in real projects.

### Pin Provider Versions

Always specify version constraints for your providers. The `~> 5.0` constraint means "any version in the 5.x range." Without version pinning, a provider update can introduce breaking changes that alter your infrastructure unexpectedly.

```hcl
required_providers {
  aws = {
    source  = "hashicorp/aws"
    version = "~> 5.0"
  }
}
```

After running `terraform init`, Terraform writes a `.terraform.lock.hcl` file that records the exact provider versions installed. Commit this lock file to version control so that every team member uses the same versions.

### Use Remote State from the Start

Even for small projects, storing state remotely with locking prevents a class of painful bugs. Set up an S3 backend (or equivalent) before your first `apply` in any shared environment. Retrofitting remote state after infrastructure already exists is possible but more disruptive than starting correctly.

### Treat Plans as Code Review

In a CI/CD pipeline, generate a saved plan file with `terraform plan -out=tfplan` and require a human to review it before running `terraform apply tfplan`. This is analogous to requiring pull request reviews before merging code. The saved plan ensures that what was reviewed is exactly what gets applied, with no possibility of drift between review and execution.

### Keep Secrets Out of Configuration

Never hard-code passwords, API keys, or other secrets in `.tf` files. Use variables marked `sensitive = true`, inject values through environment variables (Terraform reads `TF_VAR_<name>` automatically), or integrate with a secrets manager such as AWS Secrets Manager or HashiCorp Vault.

### Estimate Costs Before Applying

Tools like [Infracost](https://www.infracost.io/) can analyze a Terraform plan and estimate the monthly cost of the resources being created. Adding cost estimation to your review process prevents surprise bills, especially when resources like NAT Gateways, RDS instances with provisioned IOPS, or data transfer are added to a plan.

### Organize with a Consistent Structure

A typical Terraform project separates concerns across files:

```
main.tf          # provider config and primary resources
variables.tf     # all input variable declarations
outputs.tf       # all output declarations
terraform.tfvars # default variable values (environment-specific)
```

This convention is not enforced by Terraform (it loads all `.tf` files in a directory), but it makes configurations easier to navigate and review.

## Takeaways

Infrastructure as Code transforms infrastructure management from a manual, error-prone process into a disciplined engineering practice with the same review, versioning, and reproducibility expectations as application code. Terraform achieves this through a declarative model: you describe the desired end state, and Terraform calculates how to get there by comparing that description against a state file that tracks what currently exists in the cloud.

The core workflow (init, validate, plan, apply) is a deliberate checkpoint system. Every change produces a readable plan before anything touches real infrastructure, and saving that plan to a file creates an exact contract between what was reviewed and what gets applied. State is the mechanism that makes incremental changes possible; protecting it means using remote backends with locking, encrypting at rest, and keeping it out of version control. Variables and modules make configurations reusable across environments and teams without duplicating code. The dependency graph handles ordering automatically, and the rare explicit dependency (`depends_on`) covers the cases where the graph cannot infer the relationship from attribute references alone.

Terraform does not stand alone in a real automation stack. It handles the provisioning layer: creating VPCs, security groups, EC2 instances, and databases. The configuration management and CI/CD layers then operate on the infrastructure Terraform provisioned. Understanding where each tool's responsibility begins and ends is the key to combining them without duplication or conflict. The Configuration Management with Ansible and CI/CD Pipelines lectures cover those layers in detail.
